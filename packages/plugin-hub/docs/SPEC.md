# Hub v3, the spec

One line per rule. Derived from the decision record, which holds every ruling and its history. Regenerated whenever an entry changes. A build session reads this first and opens a decision entry only when it needs the why. Every `Forbidden` and `Check` line below is a seed for the failing tests written before any code (D8). Written 2026-09-14 after the blind review and the attack pass.

## 0. Frame

- The hub is imprnt's connectivity plugin and nothing more: messages between people and their agents, the record of what was said and what is owed, a few watchers, gates on anything that leaves the house.
- Ours: the vault, the rules, the doors, the runner, the ledger, the watchers, the gates. Rented: the loop (Claude Code, Codex, OpenCode), the model, the transcriber, the browser, the database, the OS service manager.
- Blank page: no v2 piece is kept because it exists, only because an entry names it (D4).
- Not hub rules, dropped: review loops (L8), "the hub never edits itself" (L9), rules about tests that cannot fail (L15), the model inventing facts (L16).

## 1. Machines and the store (D5, D7, L7)

- The Pi is always on and runs the hub. Pi off means no work, by design. The Mac and the PC are executors: one runner each, controlled from the Pi over the tailnet, never a door, never the record. Another person installs the whole hub on a normal Mac or Linux box.
- One Postgres on the Pi holds every message, reply, job and turn for every person and every machine. Ledger and queue in one. No NATS, no SQLite, no broker, no per-machine file.
- A row is on disk before the database says ok. Any setting that says ok earlier is forbidden.
- The table holds the work. A notification only wakes a runner. On every connect and after every turn the runner reads its eligible rows, and it wakes itself on a recorded retry or claim deadline. The transaction that makes work available emits the notification. No polling on a timer.
- Backup: a plain-text dump every hour into its own private repo on the hub box (never a vault), committed when changed, then the same weekly bundle, encrypt and upload as the vaults. The off-site destination is a setting (any rclone remote, an rsync target, or none). Maximum loss: one hour. No provider named in code.
- Measured on this Pi: 26 MB idle, about 1.3 ms per durable commit, 0.6 KB of write-ahead log per message. Measure again under real traffic: WAL per day, commit latency across checkpoints, the full peak beside the memory workload of section 6.
- Tenancy: the boundary is the person. One Unix account. Each agent's process runs in a kernel box that reaches its own person's tree and nothing else. One shared zone mounted into every vault, sharing a note means moving it there. One or more people, nothing special-cased for two. Not a defence against a household member.
- Forbidden: a second store for messages or jobs; a per-machine ledger file; a broker between two of our processes; polling where a notification exists; a runner that relies on a notification alone; a backup provider in code; a Unix user per person; a shared zone for a subset of people.
- Check: the two kill tests of section 2 against the one database. Every runner connects to the same host. A runner silent for N hours is a finding. A reconnecting runner drains waiting rows with no new arrival. The dump is younger than an hour plus grace and the off-site copy younger than its interval. The tenancy probe with its control, per agent: inside the box the other person's tree, origin and process list are empty, outside the same command reads them.

## 2. A message (L1, L6, L2)

- Two tables, one owner each: `inbound`, written by the door, and `outbox`, written by the runner in chunks. Nobody else writes either.
- Order: the door reads from the platform, writes the inbound row, commits, only then acks the platform. The runner feeds the row and marks it sent only when the loop acks that exact message. The turn ends, the runner writes every outbox chunk and settles the inbound row in one transaction. Only then the door posts, marking each chunk delivered after the platform accepted it.
- Delivery is machinery. An agent produces text. It never calls a send tool, names an address or presses a key, for a human or for another agent. The turn's text is the reply. A dispatched job's text is the report, carried to the dispatcher by the runner.
- Across machines: a job for a spoke is a row in the same database. The spoke's runner claims it and settles it with its reply in one transaction. A machine that is off finds its rows waiting. Spoke runners are OS units, started at boot, reconnecting forever.
- Feed order: rank 0 is anything a human is waiting on (a human's message, a report on a job that answers a human's message), rank 1 is proactive work (watcher triage, rooms, harvest). Oldest first within a rank. One message per turn, never added to a running turn.
- Five stamps per human message, written by machinery, never by the model: received, acked, started, answered, delivered. Metrics: time to ack (product, alerts), time to start (technical, alerts, says whether the model is down), ack to start and answered to delivered (technical, alerts, loop speed), time to delivered (product, no alert). Defaults until measured: acked in 30 s, started in 60 s, answered in 15 min, delivered 60 s after answered. Thresholds are one table per person in the registry. The board shows p50 and p99 per person and per agent, today and this week.
- While a turn is open: typing on Telegram and Discord refreshed every few seconds, and one progress card in the chat shows the turn's observed progress. Ordinary-turn clock reasons update that card, in the person's language, saying it is the door speaking; the clock evidence stays in the diary and the chat log. Completion records the desired final totals durably, not guaranteed delivered totals: uncertainty or refusal can leave the visible card unchanged. A running door waits at most five seconds per reply chunk for the card's final content while the effects task exists; startup skips the wait until that task exists, so a reply may precede the final edit.
- A silent day is never a finding. Acceptance at build time and at every cutover: a human sends one real message per person and gets a real answer. Never a script.
- Chat log: the door appends every message in both directions to one dated file per agent, before sending. The loop's session is a cache. On every spawn of a fresh master session the runner hands it the tail (24 hours, 8k tokens, defaults until measured) as delimited background on the FIRST real input it is claimed for: one feed, one model turn, one answer. History is never a turn of its own, an eager start feeds nothing, and a resumed session is not handed it again. The conversation's own entry for that input is the input as it was sent, without the background. The agent never chooses what to read on spawn. No per-agent tail size.
- Forbidden: a cursor that moves before the inbound commit; a send before the settle commit; a reply that depends on the model calling anything; a second writer on a table; a message or job stored outside the one database; a report on a human's message fed after a later human message; a turn open with no typing shown; an expired clock with no chat line and no finding; a stamp written by the model; a synthetic test message; a door declared healthy from its own stamp while a real message waits; a fresh master session answering without the tail it was owed; the tail run as a model turn of its own.
- Check: kill the door between read and ack, restart, the message is answered exactly once. Kill the runner between turn end and settle, restart, the reply appears exactly once. A turn with no tool call still lands. A report on a human's message is fed before any human message that arrived after it. Every human row older than a threshold with the next stamp missing is a finding that clears when the stamp lands. A code word planted in the log survives a respawn.

## 2a. Conversations and attempts (IMP-227)

- Four things that used to be one: a job is an assignment, a turn is an `inbound` row, an attempt is an `execution`, a conversation is what the engine remembers. A master has one conversation for good. A new job has a fresh one even when the same configured worker served the last, and an explicit follow-up (`dispatch.conversation`) is put into the one it names, or refused by name. A worker's context is its brief and its own transcript, never a seat's chat tail.
- The engine session is the conversation's own, for a master as for a worker: chosen by the hub, launched under that id the first time and resumed under it after (`--session-id`, `--resume`), never "the latest", and stable across an idle shutdown and a restart, so a completed master turn is resumed and not primed again. The conversation's directory outlives the child. What the engine reports as its session is kept apart from what was asked for, and a difference is written to the diary. A session a child was launched under and the engine never acknowledged (`launched`) is not taken for a new one and not resumed as a known one: it is replaced by a fresh id, durably, and the diary says so.
- An attempt is owned before anything launches, and the opening is the fence: one statement inserts it only while the input is still claimed by that runner, that runner incarnation is the registered current one and the conversation is on the placement generation it planned with, and the table allows one unresolved attempt per conversation AND one per agent, so two jobs of one worker cannot both start. A stale generation, claim or incarnation is refused, never substituted. A lease that ran out proves nothing about the process. A fresh master child is NOT primed by a model turn: the chat tail it is owed rides as background on the first real input's one feed (the feed intent's diary line names it: kind, digest, size), so there is no attempt, no feed and no model turn for history alone, and the eager start of a resident opens no attempt and feeds nothing. Only the wire text carries the background: the conversation's entry, the attempt's input digest and every recovery read the input without it, and history is never put into a transcript it did not come from. A child whose native session is resumed already has its history and is not handed it again; a start that failed before the input's feed intent is retried with the history (nothing was handed), and one that failed after it is held like any other, with no history replayed on the owner's continuation. Earlier builds fed the tail as a model turn (an eager attempt with `purpose = 'tail'`, or a `tail_fed` feed intent on a claimed row's attempt): what such a build left unresolved is resolved by the same rules as any attempt (interrupted only on proof, otherwise `unknown` keeping the slot, the input held) and is never resumed or fed again by this build.
- The feed intent is committed before the first byte reaches the engine, under the same fence, after what is known of the processes (leader, tree, process group, machine, boot) was recorded. From then on a crash, an exit or a killed child is uncertain, and machinery never feeds that input again: the exclusion (`hub_row_held`) is durable and is not undone by resolving, releasing or continuing anything, and the input is not stamped answered either. ABSENCE OF OUTPUT OR OF A RECEIPT IS NOT NON-DELIVERY, and background that rode with the input is part of that one feed. The only proof of non-delivery is the adapter's own `FeedNotWritten` (it refused before a byte was written: the session was already closed or its process already gone), and even that lets the input be tried again only when nothing else was fed to that attempt first and it has done nothing; a write or a flush that failed, a pipe that broke, a rejection with no name stays uncertain, held, exactly like a crash after the call. A TERMINAL REFUSAL by the loop (a login refused, a window used up, any `is_error` result) after the feed holds the input the same way, with the exit proof of the child the adapter closed and what was known of its effects, and nothing feeds it again: not the end of the outage, not a generic recover, not a restart, not the passing of a retry. The engine's own API backoff (429, 503) stays inside the one running attempt and is not a failure. What was never handed to the engine waits: after a refusal the agent's other unfinished rows wait out the recorded interval (or the window's own reset) instead of being fed one after another into an engine that just refused, and a refusal the engine was handed carries no retry. What was produced is journaled before the settle. A journaled result is never turned into an interruption: a failed settle, or a stop that lands between the journal and the settle, leaves it journaled and it is settled from the journal (without asking about generation or incarnation, and without a model) on the next start or the runner's next look.
- An attempt that ended without a result is `interrupted` only on positive evidence, `unknown` otherwise, and the input is held (`replay_hold`). Positive evidence is either a new boot of the same machine (every process of the earlier boot is gone; a boot is told by the kernel's per-boot session id, `boot_id` on linux and `kern.bootsessionuuid` on macOS, recorded as `<scheme>:<uuid>`, and by nothing that moves with the clock: `kern.boottime` shifts whenever the calendar is set and is never read, a platform that will not answer has no identity, and an identity that is missing, malformed, untagged or of another scheme is never read as a different boot), or a BOUNDED claim about the managed process: the child led a process group of its own (asked of the runtime and read back from the process table), the system says that group is empty, every process ever recorded under it is gone (the record is the union of every look, never only the last one), and its leader exited. A lookup that FAILED (an error that is not "no such process", a process table that would not be read) is unknown and never gone; a recorded process that is still there, a detached survivor included, keeps the attempt open; a record with no verified group proves nothing, however many of its processes are gone. An old incarnation, an empty list, an expired lease, a missing `processes()` and a refusal by the loop (which leaves its process alive) prove nothing. Not covered, and said by the diary's `basis`/`via`: a process that left the group (its own session or group) before anything recorded it, and every effect outside the process table (a file, an API call, a message): nothing is rolled back or claimed undone, and the owner is told what is known. `unknown` keeps the slot; only proof moves it. A fresh turn beside a held input starts only on an engine build whose resume was validated and whose session the engine acknowledged, is told not to continue the assignment (and the context counts as told only once the engine has it), and explains what is and is not known. The owner's choice (`/recover <agent> <attempt> <revision> continue|keep-held|fresh-context`, or the hub's tool) names one attempt at one revision; `continue` queues one linked new input once the attempt is over. `/recover <agent>` restarts plumbing and lifts nothing. No context is rebuilt automatically. The explicit `fresh-context` choice (`fresh_context` in MCP) discards native context only after the named attempt is terminal with confirmed process exit and the agent has no unresolved execution. It closes that hold, changes the native session ID and placement generation, and permanently gates any earlier queued continuation. The original input remains excluded by its interrupted execution. A fresh message receives the known-effects warning; unfinished work requires a new owner request. Other open holds and lifecycle gates still apply. A started conversation remains bound to its engine, including after this reset; an engine mismatch parks the runner until configuration changes. WHAT A HELD CONVERSATION IS WAITING FOR IS SAID, not only that it is held: the runner measures, for each terminal hold, whether the conversation can take a turn on a native context that resumes (the engine shown able to, and a session the engine acknowledged), records it on the hold for that attempt at that revision and engine (`native_context`: ready, unavailable with its cause, or pending), and tells the owner once per attempt, revision and cause (`context:<attempt>:<revision>:<cause>`) even when the engine's answer filtered every row of the conversation out before any claim. The owner's choice is recorded whatever the context is: the answer to `/recover … continue`, the hub's tool and `check` say "waiting for native context (cause)" or "pending verification", and only a context measured usable is called queued behind the current turn. What was measured on another engine or configuration is never shown as current: it goes back to pending when a runner starts or stops, and a launch uses the engine's own answer (read at most thirty seconds before) and blocks by name when it is not yes. No rebuilt context and no automatic fallback stand in for it.
- A settle completes its attempt in the same transaction, and only while the attempt is still that runner's CURRENT incarnation and the conversation is still on the placement it began on.
- The hub's tool facade (`hub_topic` and `hub_council`) is a stdio server the engine starts, bound by the runner to the conversation it launched. It has no database login and no argument names whose call it is. Source evidence and idempotency are checked in the transaction that applies the call.
- Native delegation, team, workflow, background and scheduling tools (`Agent`, `Task`, `TeamCreate`, `TeamDelete`, `SendMessage`, `Workflow`, `ListAgents`, `TaskStop`, `RemoteTrigger`, `CronCreate`, `CronDelete`, `CronList`, `ScheduleWakeup`, `Monitor`, `EnterWorktree`, `ExitWorktree`, `PushNotification`, `ReportFindings`, `DesignSync`) are denied by name in every launch, and the tool list is always an explicit one. An agent's own list is passed as configured (and refused if it names one of these); an agent with none needs a validated ordinary profile for the installed build and is refused by name without one (`ordinary-tool-profile-unvalidated`). `delegationDisabled` and `safeResume` are true only for builds somebody validated by running them, and an ordinary launch on any other build is refused by name and version (`native-tool-control-unvalidated`), as is a configured builtin the build was not observed with (`tool-profile-unvalidated`). The person's own MCP servers and the agent's primary model are passed exactly as configured: nothing is substituted. This is not a sandbox: a shell can still call a model API.
- MEASURED SCOPE, and nothing wider (Claude Code 2.1.285, Sonnet 5.5, Hub's own stream-json input, replay and partial-message flags, on the maintainer's Mac): with an explicit `--tools` of the nine ordinary tools (`Bash Read Write Edit Glob Grep NotebookEdit WebFetch WebSearch`) and one stdio MCP server, all nine were exposed, the server connected, and none of the denied names or any unrequested native tool was present. A CLI killed abruptly (SIGKILL) after one MCP tool call had made one fsynced effect, with its `tool_use` durable and no `tool_result`, was resumed under the same session id with a NEW question: it kept its marker, made no tool call, and the effect count stayed 1 → 1 (the CLI wrote an interrupted-tool error for the unfinished call and did not run it again). That is what puts 2.1.285 in the validated tool-control, ordinary-profile and safe-resume tables, and 2.1.284 in the tool-control table for the restricted Read/Glob/Grep list only. It is not evidence about shell effects, detached descendants, other tool profiles or builds, another machine or the Pi, a person's box (the facade is exercised inside the box by its own test), or a resumed model that chooses to act: nothing prevents an autonomous semantic choice, a shell command or an API call.
- MEASURED SCOPE, Claude Code 2.1.286 (the same claim as 2.1.285 above, measured ONCE, Sonnet 5.5, Hub's stream-json input, the maintainer's Mac, the owner's normal CLI login, UNBOXED, a synthetic fixture and no real user history; one run of the existing reviewed interruption probe, script sha256 `85f29e1b76164a7e61f0c4719aaae3c4a9041f1f986bc530b1aff94d50802414`, against the binary sha256 `75e3016e9d2570767b08e43a7467d4817a4f149232c169ca295f2c95fef21433`; the binary and the `claude` symlink were unchanged across the run). Observed: verdict PASS_SCOPED; in both phases the init tools were exactly the nine ordinary tools plus the fixture server's one tool, the server connected, nothing denied or unrequested; phase 1 had one fsynced effect and a durable `tool_use` with no `tool_result` after SIGKILL; phase 2, the same session id with a NEW question, kept its marker, made no tool call, and the effect count stayed 1 → 1, with no replay of the interrupted call; weekly utilisation seen 76%. Cleanup was verified, with one caveat kept as recorded: the phase 1 group cleanup logged `killpg SIGTERM: PermissionError`, after which the probe's own SIGKILL succeeded and the group was gone. A separate Mac init-only probe used the unchanged production `makeLoopLaunch` argv/env/cwd and sandbox wrap, with synthetic invalid credentials: exactly the nine builtins and one connected fixture MCP tool, no denied or unrequested tools, requested model/session/version matched, cleanup verified, no credential file copied into the session. It stopped at init and observed no model answer, tool execution or resume. Neither probe establishes shell-effect replay behavior, detached-descendant termination, other profiles, another machine or the Pi, a real user box, or what a resumed model chooses to do. CI remains pinned to 2.1.285.
- The protocol is activated by the first runner of protocol 2 that starts; from then on every claim by the runner role must say it speaks 2 (a transaction-local setting, so a pooled connection carries nothing over), and any other is refused by the table. The claim and the activation are ordered by a ROW LOCK, not by a clock or a deploy instruction: a claim that does not say it speaks 2 reads the protocol row `for share` and keeps that lock to the end of its transaction, and the activation (an update of that row) waits for every such claim, then looks for in-flight inputs after it has waited; an activation in flight makes a late old claim wait and then be refused. A claim that says it speaks 2 takes no lock. It is not a lease or a broker. A scheduled harvest asks the same ownership question as any other claim: an attempt whose ownership is unresolved (`unknown`, `stop_unknown`, `stop_requested`), or that belongs to another runner or to an incarnation that is no longer current, holds it; only the claimant's own live turn lets it run beside. Landing the step, and activating the protocol, are refused while an input a runner of protocol 1 may have handed to the engine is in flight (unanswered and acked, started, or claimed and received, with no attempt): stop the old runners and settle or discard those inputs first. A council member that is held or whose attempt is unresolved is never given up on, by the runner, the door or the store: nothing abandons a council member (section 2b).
- Forbidden: a second live or unresolved attempt for a conversation or an agent; an interrupted input claimed again, by any path, for any reason; a claim that reads an expired lease as a dead process; a capability assumed and not read from the engine; a conversation rebuilt silently from its transcript; a model-supplied identity, route or approval on the tool facade; an exit inferred from an incarnation, an empty list, or a refusal.
- Check: kill the child after the feed and the input is held, the owner told once with the command that decides it, and nothing fed again (not after the owner's continuation either); a runner that dies inside the settle, or whose settle failed, leaves a reply that appears exactly once with no second feed; an attempt whose process is still there keeps every other row of the agent waiting until it is gone; two jobs of one worker opened at once start one; a runner written before this section is refused every claim once the protocol is active.
- OPERATIONAL PIN, before any rollout: the model CLI on every machine that runs an ordinary agent must use a measured build (2.1.285 or 2.1.286), with auto-update off to prevent drift; CI remains pinned to 2.1.285. An unmeasured build is refused by name at launch (ordinary agents) or waits for the owner (interrupted conversations), so a CLI that updates itself takes every ordinary agent offline. The pin, the auto-update setting and the accounts are the operator's; the hub changes none of them, and adding a build to the validated tables needs a measurement, not a version bump.
- Not yet true, by name: `safeResume` and the ordinary tool profile are validated on Claude Code 2.1.285 and 2.1.286 only and for the scope measured above (any other build waits for the owner, and an ordinary launch on it is refused); Pi, other machines and detached-descendant termination are unvalidated; a process that left its group before it was recorded is not shown gone by anything but a reboot; nothing rolls back an effect outside the process table.

## 2b. Councils (IMP-228)

- A council is a durable object (`council`, `council_participant`, `council_round`, `round_member`, `council_decision`, `council_event`, migration 14), started by the agent's `hub_council` tool (`start`, `continue`, `inspect`, `stop`) and never by the door alone. `/council` and `/совет` are the owner's own message to the agent, marked `command = "council"`; the old door behaviour (every configured seat, one merge) is gone. Identity is the runner's binding, never an argument; every change carries a `request_key` and, unless it makes a council, the `expected_revision` `inspect` showed; the owner's own messages are named by id and code checks they are the owner's, sent to this agent, newer than what they authorize and not spent on another request. Code cannot check that the words mean "a council" or "these three", and nothing pretends it can.
- The roster is explicit and exact. A participant is a configured worker (an agent of the person with no door and no chat) resolved to the preset and the machine its registry entry gives it, recorded as a snapshot; a request that names a different preset or machine, an unknown or duplicate worker, or fewer than two is refused by name, and a roster that is not fully named returns `needs_participants` with the real choices and writes nothing (no council, no job, no card, no invocation). An owner's explicit request starts at once. An agent's own proposal is frozen whole with its resolved roster (`council.start` confirmation) and starts only on the owner's reaction, acted on in the approval's own transaction; a worker's proposal is pinned to the master and owner of the job it is doing, inherits no authorization, and a worker whose configuration changed by approval time is recorded missing, named, and not started under its old name or swapped.
- Each participant is an ordinary job with a conversation of its own; a follow-up, a debate round and a correction's continuation are put into that same conversation. Debate is opt-in: saved at the start, or recorded from fresh owner messages that ask for it, including after an independent comparison completed. There is no round cap; the master decides when another round adds nothing.
- State is read off the rows, never guessed and never written by a clock. A member is answered when its report exists, missing when its attempt was interrupted, its ownership is unknown, it was stopped, it was refused (including a refusal because its worker's configuration is no longer the approved one), or it failed before the engine was handed its input (the job is gated in the transaction that ends the attempt so it is not tried again; a launch that failed before ANY attempt existed, or whose claim a loop or a process left behind, is fenced the same way from what the store shows: a claim is not a retry barrier, so a council job a runner still holds with no attempt that may be running and no hold is gated and released, by the failure path itself and, mandatory and before it claims anything, at the start of every loop of that agent and on the owner's recovery of it, and a store that cannot take that write leaves the claim held and the loop claiming nothing until it can), and open otherwise; queued, waiting for its machine, waiting for capacity, running and quiet are told apart from the job, its attempt, the runner's wait and the loop's own activity. A quiet or slow worker is only flagged and never stopped, retried or called failed. A missing member puts the council in `waiting_owner` with the cause named and healthy siblings running; nothing is rerun, replaced, left out or synthesized without an owner decision recorded on the council (`wait`, `retry`, `replace` as a new participant linked to the old one, `use_available` naming the omitted members before a result with fewer answers can be finalized, `extend`).
- The master's queue entries are the hub's own rows (`council-event:<council>:<n>`, kind `report`, rank 0), written once per condition and stamped with the moment they are written (`clock_timestamp()`, not the request's time), ready at the commit; an already waiting human message stays ahead of one and a later message cannot jump it. The council becomes `assessing` when the feed intent of the master's attempt consumes the event. It is COMPLETE only because the master called `finalize` from an attempt of its own (whatever input that attempt answered, the event or the owner's message that chose) and that attempt settled: the reply that settle writes is the result. A reply with no finalize completes nothing, and the council goes back to waiting for its master.
- The checkpoint is wall time from the start of the current authorization epoch, persisted (`council.checkpoint_minutes`, 30). Crossing it lets a running round finish and allows synthesis; it blocks starting further work (a debate round, a retry, a replacement, and the corrected input of a correction) until the owner extends it by minutes or by a number of rounds, recorded with their messages. Only an owner-requested follow-up starts a new epoch; a model's round and unrelated messages do not reset it. A blocked debate, retry or replacement is not recorded and spends nothing; a correction is the exception (next item).
- A correction names the affected participants, and it is accepted, journaled and acted on at any time, before or after the checkpoint: the owner has said the work on the old question is outdated, and stopping it is not starting further work. Work not yet started is gated; a running attempt is asked to end with a durable stop request, now. The corrected input is fed only once two separate facts hold: the attempt is shown to be over (the existing recovery choice for an interrupted input, with the correction as its context, or a fresh input into the same conversation when the attempt had finished or never started), AND the checkpoint lets further work start. With the checkpoint closed the correction is saved on the council, the council waits for the owner (`waiting.kind = 'checkpoint'`, named on the card and in a once-per-revision notice), the old hold is not released and nothing is fed; the owner's scoped extension starts every participant of that correction together and spends a rounds allowance once for all of them. The deadline and the period are not moved by the correction. What a superseded input produced is kept and never satisfies the round. `stop` and a correction FENCE FIRST and read what is owned after: every job the council owns that is not answered (found by the jobs' own provenance, so every round, a participant that was replaced or left out, a member whose ownership is unknown, and the continuation a retry queued) is gated in ascending agent order, and only then are the council's attempts read and each running one asked to end by a durable stop request frozen to that attempt (`council/fence.ts`, using `hub_gate_place`'s ordering lock against the opening of attempts); a member is `cancelled` only when, after the gates, nothing of its work is owned, and a council is `stopped` only when no member is waiting, no attempt of any of its jobs is owned, and no job of it could still be claimed. A correction's no-hold branch asks the same question again under the gate (no hold is not proof of no live attempt). An owner's earlier retry that was still waiting for a process to be shown over (`continue_pending`) is superseded by the later stop or correction with the store's own current-revision choice (`keep_held`), and its result is checked: if the continuation was queued first (`closed`) it is found, gated and its attempt asked to end, and it is never taken for the corrected work (only a continuation the correction itself made, with its question revision and context, may become the corrected input). A question or an unrelated message changes nothing.
- A council that is complete or stopped starts work only through the owner's own follow-up (a new authorization epoch, in the same conversations): a debate round (opted into or not), a retry and a replacement are refused with the way back named, so a terminal council is never reopened behind the owner's back; inside the new period an opted-in debate is the master's own step again, and a debate can be opted into later on fresh owner words as before.
- Two parts of the settlement are not hooks that may fail. The council's result is recorded in the same transaction as the master reply's settlement (`afterMasterSettle`): if it cannot be recorded the settlement does not commit, and the runner, which journals the model's answer before it settles it, settles it again from the journal without another input to the engine; the consumption of an event by the master's attempt is written by the feed intent's own transaction. A council still preparing its result after that attempt was settled, or long after it ended without one, is said by `check` as `council-finalizing` and on the card. A member whose attempt fails before the engine is handed its input is fenced by the transaction that ends the attempt (`endAttempt` writes the `council-failed:<job>` gate, mandatory); if that write fails the attempt stays owned and its row is not eligible until a restart ends it and writes the gate. Only optional bookkeeping (a reconcile, a wake) runs in a savepoint, and it requires a real transaction.
- Every job of a participant is launched under the profile the owner approved (`council/profile.ts`, `council/launch.ts`): the participant is accepted with its worker, preset name and five settings, tools, instruction/settings/MCP file names, runner and machine (names and lists, no credential), and the runner compares the digest again before it chooses a conversation or starts a child, for a first input, a later round, a follow-up, a correction, a retry and a recovery continuation alike. A worker that no longer matches is refused by name (`configuration changed`, with the parts that changed and never a value) and read as a missing member waiting for its owner; nothing is fed, retried, replaced, disabled or rebuilt.
- One card per council (`council-status:<id>`) is written through `platform_effect` from the rows and coalesced: at most one write in `council.status_write_seconds` (5), at once on a stage change, otherwise after `council.status_edit_seconds` (10) and only when the words changed. The words include the elapsed time in whole minutes, so the card is edited in place as a minute turns (one card, one edit per displayed minute at most, never a second message and never a second write of the same words). What needs the owner (a missing participant, quiet after `council.quiet_minutes` (5), one attempt over `council.overrun_minutes` (30), the checkpoint, a master turn that did not finish) is said once per condition in the council's chat and in the person's General (`general` on their table, an agent id). With no usable General the council's own chat says so by name, and nothing goes anywhere else.
- While a council is active its master keeps one slot and one child's memory free on its own runner, once per master however many councils it has; a worker (an agent with no chat) is not admitted into it, nothing is stopped to make room, no other machine is chosen, and where the limits leave no room the wait says so. The decision is made once, after the council query is answered (`runner/admission.ts`): the runner's reservations, measured memory, limits and resident masters are read after that await and the count, the memory check and the reservation are one synchronous step, so two workers that wake together cannot both take the memory beside the master's reserve.
- Migration 14 reads the old council sheet and the merged councils behind it into these tables: a merged council is history and inspectable; an open one is `origin_kind = 'legacy'`, its seats read from their jobs, reports and holds (a held seat is read from its hold and keeps it, the cause and the conversation history), waiting for its owner when any is missing, and it is only ever inspected or stopped. Nothing of the old design is merged, abandoned or replayed; `hub_council_abandon` and `hub_council_merge` return false (the merge rows already written stay as history). The old design's writers are closed in the database and not by anybody having been quiesced: a job that names an old council (`dispatch.council`) and does not continue an interrupted one (`dispatch.continues`, which the store's own recovery writes for a held seat) is refused at insert, so an old door's next council fails in its own transaction; the step takes the sheet and then the queue lock at its start, so an old settle that had read its sheet row finishes (its merge included) before the old councils are read, and one that had not meets the rows gone (the old settle returns when its sheet row is missing). Runner protocol 3 fences an old runner and says nothing about an old door; the door must be upgraded with the step.
- The runner protocol is 3 in this build (`RUNNER_PROTOCOL`, `store/conversations.ts`), through the machinery of migration 11 and no other: `hub_protocol` allows 1, 2 and 3; a runner says its protocol on every claim (`hub.runner_protocol`, in the claiming transaction); the claim trigger refuses a claim that says less than what is active; the incarnation row refuses a registration that speaks less than what is active; and, independent of what is active, a council's job (`dispatch.council_round`) and the events the master reads for a council (`council_event`) cannot be claimed by a connection that does not say 3, so an old runner cannot settle one as an ordinary report. Landing migration 14 activates nothing; a runner of this build activates 3 when it starts (after `requireSchema`, which refuses a store before migration 14 by name, and before it registers or claims), moving only forward and only when no input an old runner may have fed is in flight. Activation starts, stops, settles, discards and replays nothing. The live store is at protocol 2 until that runner starts, and nothing here says otherwise. See `operations.md` for what a release must do around it.
- Not yet true, by name: no live engine, machine, Discord or database run has proved any of this, and adapter capability (a stable session for a follow-up) is enforced at job time by the runner's named refusal, not at acceptance; the `general` setting and its shared accessor belong to the topic work and `council/general.ts` is the seam until they land; an owner's General on another door than the council's is delivered by that door.

## 3. Loops, presets, adapters (L18, D11, D12, D3)

- A preset is a bundle: model, provider, thinking effort, how it is paid. Named in the registry (`daily`, `cheap`, `heavy`). An agent points at one. The preset ID is computed from the settings, never typed. Identical settings share an ID.
- Every turn records the preset ID, the tokens the loop reported (input, cached input, output), the price when knowable from a dated rate table in the registry, otherwise plan usage as the loop reports it. Record everything the loop gives, never guess a number.
- Changing a preset is a registry edit picked up on the next turn. A price change is a rate-table edit.
- Three adapters in `adapters/`, one file each, built in this order: Claude Code first (the Max plan runs only on it), OpenCode when the bake-off names its model, Codex only if the ChatGPT plan stays. The seam is built with the first adapter. Each does exactly five things: feed a message, report the receipt, stream text, report the end of turn with usage, resume or start a session. The rest of the hub sees one field on the preset: `adapter`. Where a loop lacks a verb the adapter reports it and the runner behaves the same for every loop without it. All three driven headless.
- OpenCode: one process per agent, in its own box. One process per person is the fallback only if the bake-off measures OpenCode too heavy for a few resident processes, at the cost of the per-agent fence and crash isolation. OpenCode takes a model on every message, verified.
- The bake-off, parked, run by the owner when picked up, probably on zero-retention routes: OpenCode on the Mac in the vault folder, `/model` mid-session, the same twenty vault questions, a few Russian transcripts, the rule files loaded. Under 15 USD on keys, under 30 with Opus on API. Keys: direct for DeepSeek and GLM, OpenRouter for Qwen and Kimi, cheaperinference only on the owner's word and never with vault content. No hub code. It gates the OpenCode adapter's model, not the start of the build.
- Forbidden: a model or provider name hard-coded outside the registry and the adapters; a turn without a preset ID; a typed preset ID; a guessed price; loop-specific code outside `adapters/`; a branch on the adapter name anywhere but the adapter registry; a feature that exists only when two loops are installed.
- Check: every turn's preset ID matches the registry at that moment and carries token counts. The swap test: change `adapter` on a running agent and nothing else, the next message is answered by the other loop, for every pair. Every OpenCode agent has exactly one process, in its own box.

## 4. Harvest (L19)

- Harvest: a separate model reads a chat and files what was worth keeping through the normal ingest path. "Persist" and "wrap up" are retired.
- A watermark per chat log, advanced only after the filing landed. Three triggers: the chat goes quiet (no message for N minutes) and the slice is at least the minimum size; the daily backstop over yesterday, small slices merged; "harvest this" on demand.
- The harvester is its own preset: a fresh session with no chat context, given the slice and the filing rules. `{inferred}` on its own conclusions. "Nothing" is a valid answer. One line back into the chat, per person (a setting, on by default for the owner). File-as-you-go stays every agent's habit.
- Three knobs per person in the registry: harvester preset, quiet timeout, minimum slice. Defaults per model, set at install. Each chat harvests on its own, the triage chat included (restricting it is deferred, Whenful 16720).
- Forbidden: a slice harvested twice; the watermark advanced before the filing landed; a harvester that sees chat context; deleting an unharvested slice; a harvest cost that cannot be changed in the registry.
- Check: every watermark is younger than its last quiet period plus the daily backstop. Every harvest turn carries its preset ID and tokens.

## 5. Watchers and gates (L3, L5, D6, L12)

- A watch is a file you edit, one per thing hunted: `target` (query, site, radius, poll interval), `hard` (a closed list: max price, min price, exclude words, seller kind; an unknown key refuses the file), `soft` (prose for the master, code never reads it), `on_hit` (`notify` or `triage`).
- Every tick, in code: fetch; drop what was seen with no change (reason `seen`); re-evaluate a seen listing whose price changed, the audit row carrying old and new; drop what fails a hard filter with the filter's name and the number it lost by; the rest are hits. A notify hit: the door posts it to the person, zero model turns. A triage hit: one message to the master per tick per source with the listings and the soft prose, one model turn. The master answers with one of three verdicts: tell the person (one line, why), ignore (why), draft (sits until approved).
- A fetch that parses zero listings where the last snapshot had some, or where the page carries listing markers, is a failure notice with the snapshot kept, never an empty market.
- The audit, one row per listing, human-readable, in `#watch-audit` and in a file: when, watch, listing, old and new price, outcome (drop, notify, triage), reason, the master's verdict written into the same row, what reached the person.
- Watchers are programs with no hands. No model fetches, filters or decides in one. A hit is a typed record (`price`, `title`, `seller_text`, `listing_id`, `url`), every string capped and stripped of anything that could close a field. No guillemets, no symbol carrying a safety claim.
- The triage master has no shell, no writes and no network. Fixed in v3.0 as the first version of the ACL. Its output is untrusted: shown to the person or stored as that watcher's draft or audit row, never an instruction to an agent with hands.
- Agents with hands never read watcher text. Notices reach the person through the door, never the lair. A person pasting seller text into their own chat is their act. Known and deferred with the ACL (16720): watcher files in the person's folder are readable by every agent of that person, and harvest of the triage chat carries seller text. Until then a person rules on listings and tweaks a watch through the lair or an editor.
- Nothing leaves the house without a person's word. Replies to the asker, job reports and configured notices go to destinations pinned by machinery, no approval. A new outward action (a message to a seller, a LinkedIn reply, a `command` to another agent) is one of our own commands and refuses without an approval. The approval is the person pressing approve on the draft message the door posted: a button or a reaction, two abstract actions (`approve`, `reject`) mapped per platform by the door, the mapping a per-person setting with defaults. Bound to that exact message, single use, dies after 30 minutes. Typing "send" is gone. A model reacting or typing to itself creates nothing.
- The credential is the gate: the send command fetches its credential under the approval and hands it to nothing. The model's own login is read by the loop, the one exception. Which other credentials an agent may read is the ACL's question, deferred.
- The ACL, after v3.0 (D6, Whenful 16715 and 16720): a `can` list per agent from a closed vocabulary, presets by role, the registry row is the truth, three enforcers read it (the sandbox masks files, the loop's tool config is generated at spawn, our verbs check the pinned identity), `check` probes every right both ways, the network allowlist in the same entry. Removing a right is a registry edit that prints who held it. Until then the lair keeps its full tool set and any fence lists what used the hole before it closes.
- Forbidden: a model in a watcher; untrusted text in a session with a shell; a send path a model can complete alone; a safety rule that lives in a prompt; the master changing a watch file or sending anything; the model seeing a hard-filter drop; a right granted anywhere except the registry once the ACL lands.
- Check: every triage row gets a verdict within the runner's clock; every watcher-master turn maps to a triage row; an ad saying "message the seller now" yields one verdict and zero sends; a draft approved and then edited is refused; a reply to the asker and a configured notice need no approval; the triage master's fetch of any URL is refused; every record string passes the field-closing test; zero credential fingerprints in any agent's environment and readable tree. Closing the watcher rule: six months of `#watch-audit` without a complaint.

## 6. Running it (L13, L14, D7, L11, L4, L10)

- The registry is the list: one file names everything the hub runs for a household (doors, runners, watcher timers, the vault sync, the backup, the transcriber, the board), each with its schedule and memory limit. Nothing runs because it is on disk. The backup entry covers the vaults and the database.
- The installer generates OS service files from the list: systemd on Linux, launchd on macOS, a scheduled task on Windows when it is easy. No supervisor of ours (`supervisor.mjs`, `hub up`, `hub down` go). Start at boot, restart on death, give up after N deaths, timers and the journal are the OS's job.
- Two kinds of process: long-running services, started by the OS, and model processes and workers, started by the runner as its own children with no OS involved. One hub process per machine, ours, unsandboxed, is the only thing that talks to the OS: it watches the registry and installs, starts, stops or restarts service files when the registry changes or a restart request lands in the ledger. No agent talks to the OS.
- `check` compares the OS's truth with the list: a running `imprnt-*` unit the registry does not imply is reported red with the command to stop it, never stopped by a robot; a registry entry with no unit is reported; a scheduled job whose own success stamp is older than its interval plus a grace is reported. The board shows the list, the OS state, the difference, and acts (start, stop, restart, pause) through the same verbs as the command line, tailnet only.
- All settings live in the registry plus the watch folder. Plain text. Not there means not a setting. The installer, the web board and an editor edit the same file, and the hub notices on its own tick. The command line says what to do and to whom, never how things behave. Tests do not count as usage. A value that does not parse refuses the file and names the line.
- No routine operation restarts a process: add or remove an agent or a person, change a model, edit an allowlist, add, edit or pause a watch, rename or delete a channel, sleep or wake an agent. Every process re-reads what it needs on its own tick within seconds. Legitimate restarts: a deploy, a changed platform token, or a human asking to recover a stuck agent (from any chat or the command line, a ledger row, the hub process acts, never the agent being restarted, never the asker's own unit).
- Memory: every long-running piece has a measured peak on record (Postgres included). The runner reads each child's memory on its tick and kills it over the registry limit, one ledger line. Doors, board and transcriber are watched the same way by `check`. `check` names what the kernel could add (`cgroup_enable=memory`, earlyoom) as findings with the fix in them. The installer never edits a boot file. Voice recognition is an optional component, chunked by default in one-minute pieces, chunk length a setting.
- Credentials: one owner (the household or one person), one file, every agent using it points at that file. A copy anywhere is a finding. `check` opens every credential and asks whether it still works (blank, expired, unreadable are named findings). An outage is one notice per person naming the cause, rows the engine was never handed wait and are tried on a fixed interval, one "it works again, catching up on N messages" (a row the engine WAS handed and refused is held for its owner and is not counted, because nothing will answer it by itself: see the conversation section). A used-up plan window is the same outage, its thresholds on the preset (defaults: at 85% proactive work pauses, at 95% one line, at 100% rows wait), a per-token key has no window. v3.0 ships the shared-credential shape only.
- Forbidden: a process or timer not generated from the registry; a supervisor of ours; a job with no success stamp; two implementations of a control verb; reading "timer enabled" as "job ran"; a behaviour switch on the command line or in an environment variable; a setting the UI can set that the file cannot; a setting nothing in production reads; a quiet default on a bad value; a routine operation waiting on a restart; a process that reads its configuration only at startup; an agent talking to the OS; a service not generated from the registry; a piece with no measured peak; an installer that edits a boot file; a copied credential; a health check that does not open the credential; a per-message apology for a household-wide cause; a window threshold in code.
- Check: running units minus the registry's set is empty and the reverse is empty; every scheduled job's last success is recent; a killed listed process is back within the OS restart delay; a worker spawned from chat is a child of its runner with no service file; the routine-operations smoke shows no process id changed and every operation took effect; every setting the code reads has a field in the file; a file with a bad value is refused loudly; every resident piece has a peak on record; the memory watch is on for every child; the two kernel findings fire when they apply; a second copy of a credential is a finding; during a refused-login or used-up-window outage exactly one OUTAGE notice per person exists and zero per-row apologies (an input the engine was handed and refused also has the notice every held input has, naming the attempt and the command that decides it: that is a decision to make, not an apology, and it is one per attempt).

## 7. Records (L17)

- A diary answers "what happened, when": every entry has a time, is appended, never edited or deleted, a mistake is a new entry. The chat log, the ledger's event table, the vault's `log.md`.
- A state sheet answers "what is true now": one row per id, edited in place, a gone thing's row removed, no "fixed" or "superseded" line, no dated sections. The registry, the `check` output, the watcher audit, `DECISIONS.md`. Its history is git.
- The current state of a diary is derived by code: `inbound` is computed from its events.
- Enforced in code: appending an id that exists to a state sheet is refused, editing a diary entry is refused, both attempts are ledger events.
- Check: every state sheet has exactly one row per id. Every diary is in time order and no entry was modified after the one following it.

## 8. Method (D8, D9, D2, D3)

- Architecture first (`DECISIONS.md`, this sheet). Then the expected behaviour as failing checks, the `Check` lines above as the seed, each confirmed to fail by two different agents. Then implementation until they pass. No test that cannot fail. No implementation before its failing check exists. Mutation testing is the postscript once it supports bun.
- GSD Core for the breakdown (milestones, phases, tasks, one PR per phase), Linear as the board, a small sync we own. Spec Kit is the fallback. Provisional, possibly overkill.
- The bake-off picks the presets before any of that runs.
- The blind review ran on 2026-09-14 (Codex, blind then diff, then an attack pass on gpt-6-astra). Everything it produced and what survived is in `review/`.
