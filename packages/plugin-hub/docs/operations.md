# Operations

**Pin the model CLI before rollout.** The hub launches an ordinary agent, and resumes an interrupted conversation, only on measured Claude Code builds: 2.1.285 and 2.1.286 (`VALIDATED_SAFE_RESUME`, `VALIDATED_ORDINARY_PROFILES`, `VALIDATED_BUILTIN_TOOLS` in `src/adapters/claude-code.ts`; CI still installs 2.1.285 in `.github/workflows/ci.yml`). Any other build is refused by name and version at launch, and an update of the CLI on a machine therefore takes every ordinary agent on it offline until the build is pinned back or a new one is measured and added to those tables. On every machine that runs a runner, use one of these measured builds and switch the CLI's auto-update off, before the runner is started on this version of the hub. The hub does not install, pin or update the CLI, and does not touch its configuration or the accounts it is logged in as; that is done by the operator, by hand.

An input the engine was handed and did not finish is held for its owner, and a fed turn the loop refused (a login refused, a plan window used up) is one of them: it is not retried by the runner, whether or not the loop produced anything. The owner is told which attempt and which command decides it (`/recover <agent> <attempt> <revision> continue|keep-held`); a continuation is a new input. When the conversation cannot take a turn yet, the owner is told what it is waiting for in a second notice (`context:<attempt>:<revision>:<cause>`), and `imprnt hub check` and the hub's tool show the same cause: an engine build that has not been shown to resume, no session recorded for the attempt, or a session the engine never acknowledged. Nothing is rebuilt in their place, and the owner's choice is kept meanwhile.

Use `imprnt hub check <registry> <machine>` for findings and `imprnt hub status <registry> <machine>` for wanted and observed services. A machine can be omitted only when exactly one is declared. `imprnt hub metrics <registry> [machine]` reads the shared store, and `imprnt hub recover <registry> <target> [machine]` takes the machine last: both need it only on a household in which some machine reaches the store by a route of its own (a `[[machines]]` entry with its own `store_url`), and read as before everywhere else.

A registry written as one inline array per table, which is what an earlier converter produced, loads but cannot be edited: every registry edit finds an entry by its own `[[table]]` header, so `/agent adopt`, `/agent retire` and the board's presses are refused on such a file. `imprnt hub relayout <registry>` rewrites it into the header-per-entry layout once, through the editor's own lock and structure check, and refuses a file that carries a comment rather than drop it.

Every hub process that opens the store must be started with `BUN_FEATURE_FLAG_DISABLE_SQL_AUTO_PIPELINING=1`, and the store refuses to open in a process that was not. Without it Bun's Postgres client can hand one statement the answer meant for another, and Bun reads the variable only when the process starts. `imprnt hub` and the service units the installer writes set it for you. A script run directly with `bun run`, such as the v2 handoff or the history harvest, needs it on the command line: `BUN_FEATURE_FLAG_DISABLE_SQL_AUTO_PIPELINING=1 bun run scripts/handoff-v2.ts <manifest>`. Units written by an earlier install lack it, so after upgrading run `imprnt hub install <registry> services <hub-entry>` again before starting the hub.

Install the database with `imprnt hub install <registry> database`. The registry must name an explicit `install.admin_argv` for the database administrator. This stage creates the database and runtime roles, applies migrations, and writes `[store]` once. It gives each of the four runtime roles a generated password, writes it to `<role>.password` in `hub.secrets_dir` (`<hub.state_dir>/secrets` when that is unset) with mode 0600 in a directory of mode 0700, and hands the server only the scram verifier, on psql's standard input. Each hub process reads its own role's file when it opens the store, and no agent's box can read the directory. A rerun keeps every password that still matches its role and replaces any that does not, which is also how an upgrade over roles an earlier install left without a password closes them, and it prints the roles it changed. Restart the services after a rerun that changed a password, because a process reads its file only when it opens the store. The stage does not activate services or change database access policy. pg_hba.conf must ask the four roles for `scram-sha-256` and never `trust`, and the stage names every line that still trusts them.

Keep every door's token file inside the secrets directory and the model login outside it. Every agent's box masks the secrets directory whole, masks a token file kept anywhere else on its own, and leaves the model login its loop runs on readable. On Linux a mask on a single file is lifted in every box already running when the file is replaced by a rename, which is how most editors save, while a file inside the masked directory stays covered however it is replaced. A secret path that does not exist when a box starts is not masked in that box, only from its next start.

Use `imprnt hub install <registry> services <hub-entry>` to install that machine's declared services, including its resident hub. `imprnt hub install <registry> entry <sync-entry>` installs just the selected entry and its schedule for sync rehearsal. On Linux the service account needs lingering enabled by the administrator with `loginctl enable-linger <service-account>`. macOS uses login agents; this does not provide startup before login.

The sync runs git outside every box, so it refuses a repository whose own `.git/config` names a program: a filter, `core.sshCommand`, a credential helper, a diff or merge driver, an `insteadOf` rewrite, an `include`, an alias. Such a run fails with the cause `config` until the key is removed. A repository that needs its own ssh command, a deploy key for its vault above all, declares it on its `[[repositories]]` entry as `ssh_command = "ssh -i /path/to/key"`, and the sync passes it on git's command line for the fetch and the push. Anything else of that kind belongs in the account's own configuration, scoped with `includeIf "gitdir:<path>/"` when it is for one repository, which is the account's choice and not the file's.

A repository checked out inside a vault, such as a shared mount, is declared as its own `[[repositories]]` entry with its own branch and is listed by a sync entry. The vault's sync then leaves that checkout out of its uncommitted-change check, and the mount is fetched, rebased and pushed as its own repository. A nested checkout the registry does not declare is never synced, and unless the vault ignores it, it still counts as the vault's uncommitted change.

`imprnt hub recover <registry> agent:<id>` replaces the selected agent session and releases its claims without restarting its runner or siblings. Authorized chat senders can use `/recover <agent-id>` or `/восстановить <agent-id>` for an agent belonging to the same person. `imprnt hub recover <registry> door:<id>` requests an operator-only door restart that reads the current token file. Requests and applications are recorded in the control sheet and diary.

The board serves `/chats` and `/usage` beside the four pages it had. `/chats` lists every agent with the day and the first eighty characters of its newest chat line and links to `/chats/<person>/<agent>`, which reads the chat log files under this machine's `state_dir` and nothing in the store: newest day first, newest line first, whole days until two hundred lines, and `?before=<date>` for the days before that one. On a machine whose door is elsewhere the files are not there and the page says nothing has been said yet, which is honest rather than a gap. `/usage` reads the turn records for the last seven UTC days and the `window` sheet, and computes nothing a person could not check against `imprnt hub metrics` and the ledger. Neither page has a button. The stylesheet is written for a phone: the nav scrolls sideways, every table lays out as one block per row below 700 pixels with each value under its own heading, and no page scrolls sideways or runs a script.

A watch entry (`kind = "watch"`, `source = "sentry"`) runs once a day on its `schedule` and posts one digest into the chat of the agent it names. Its key is the file the named `api-key` credential points at, one line, readable by the hub's account and kept in the secrets directory like a door's token. `imprnt hub install <registry> entry <watch-entry>` installs its timer alone, and `imprnt hub install <registry> services <hub-entry>` installs it with the rest. Run a sweep by hand with `BUN_FEATURE_FLAG_DISABLE_SQL_AUTO_PIPELINING=1 bun run src/entry/watch.ts <registry> <watch-entry>`: exit 0 is a sweep that landed, whether or not it had anything to say, and exit 1 prints `watch-failed: <entry>: <cause>` where the cause is `login refused` (Sentry answered 401), `access denied` (403), `invalid configuration` (the key file is missing or empty) or `operation failed`. A second run on the same day updates the sheet and posts nothing, because the notice is keyed on the day. The per-issue state is the `watch:<entry>` sheet in the store, and deleting its rows makes the next sweep report everything as new.

A council is run by an agent with the `hub_council` tool, on the owner's word. `/council <question>` (`/совет <вопрос>`) typed by an authorised sender reaches the agent as an ordinary message marked `command = "council"`; the door convenes nothing by itself, and the agent asks who takes part when the message did not say. A participant is a worker: an `[[agents]]` entry of that person with a `runner` and a `preset` and no `door` or `chat`; it runs the preset and on the runner its entry names, and nothing else can be asked for it. Its jobs are `<council id>:p<n>:r<round>:i<input>` and it has one conversation for the whole council, so a follow-up or a debate round is put into what it already knows. The council is one row in `council` (its participants, rounds, inputs, decisions and events are the tables around it), and `hub_council inspect` shows the state and each participant's evidence and answers, paginated. Read the same from SQL: `select id, lifecycle, current_round, question_revision, revision from council`, and `select participant_id, round, input_revision, state, cause from round_member where council_id = '<id>'`; the ledger stream `council` has one line per start, and the control lines of the jobs are the usual `dispatch.*`. When every required answer is in, the hub writes one `council-event:<id>:<n>` row (rank 0, stamped when it is written) for the master; the master synthesizes by calling finalize in the turn that writes the result. One card per council is edited in place in the chat (`platform_effect` key `council-status:<id>`). A participant that cannot be waited for is named with the store's own cause and the council waits for the owner: nothing is rerun, replaced or left out, and nothing is merged, without their word recorded on the council. A worker with no output for `council.quiet_minutes` (5) or on one attempt for `council.overrun_minutes` (30) is said once and left running. The checkpoint `council.checkpoint_minutes` (30, from the start of the current owner-authorized period) lets a running round finish and blocks a further one until the owner extends it; a correction is the exception in one respect, because it is accepted at any time and the work it made outdated is asked to stop at once, and only the corrected work waits (saved, named on the card, in the `waiting` column as `checkpoint`) for the owner's extension and for proof that the old process is gone. Notices go to the council's own chat and to the person's General (`general`, an agent id, on their `[[people]]` table); with no General the council's own chat says so by name and nothing is sent elsewhere. While a council is active its master keeps one slot on its own runner free of workers, whatever the number of councils. The `check` findings are `council-waiting-owner`, `council-waiting-master`, `council-finalizing` (a council preparing its result after the attempt that was to write it was settled, or long after it ended without one), `council-card` and `council-no-general`. A stop or a correction gates every job the council owns (of every round, of a replaced or left-out participant and the continuations of held jobs) before it reads what is running, asks every running attempt to end, and supersedes an owner's retry that was still waiting for a process to be shown over: `select operation_id, scope_id, state from claim_gate where cause = 'council'` and `select operation_id, execution_id, state from stop_request` show it, and a council is `stopped` only when no attempt of any of its jobs is owned. A council that is complete or stopped starts work only through the owner's follow-up; a debate, a retry or a replacement is refused there with that named. A participant is accepted with its effective profile (worker, preset and its settings, tools, instruction/settings/MCP file names, runner and machine): `select id, profile_id, profile from council_participant`. The runner compares it before it launches any job of that participant, and a worker that no longer matches is refused by name (`select subject, detail from ledger_event where kind = 'dispatch.refused' and detail ->> 'cause' = 'configuration changed'`, `changed` names the parts, never a value) and read as a missing member, so put the configuration back and let the owner choose, or let them replace it. A member whose attempt fails before its input is fenced by the transaction that ends the attempt; if that write itself fails the attempt stays owned (`claimed`) and its agent blocked until the runner is restarted, which ends it and writes the fence. A member whose launch fails before any attempt exists (the profile check, the conversation, the opening itself, a store that goes away), or whose claim a loop or a process left behind, is fenced from what the store shows: a claim is not a retry barrier, so at the start of every loop of that agent, before it claims anything, and in the failure path and the owner's recovery of the agent, every council job the runner still holds with no attempt that may be running and no hold is gated (`council-failed:<job>`, read as a member that failed before its input, `waiting_owner`) and released, and the runner says `council-claim-fenced: <agent>: <job>` on stderr. While the store cannot take that write the claim stays held, the loop ends and is served again after `runner.task_retry_seconds`, and it claims nothing in between: the input is never fed on the runner's own authority, and what is left for the owner is the same choice as for any failed member (retry, replace, do without it). A runner that was killed between a claim and the opening of an attempt is treated the same way on its next start, although nothing shows it failed: a claim without an attempt is not permission to feed. Ordinary work is not looked at. The councils of the old design were read into these tables by migration 14: the merged ones stay inspectable, an open one whose seats are not all answered waits for its owner and is only ever inspected or stopped, and nothing of them is merged or replayed.

**Releasing councils (runner protocol 3).** The live store speaks protocol 2 until a runner of this build starts. What a release has to do, in order: (0) know that runner protocol 3 fences an old RUNNER and says nothing about an old DOOR. The migration closes what an old door and an old runner write of the old design in the database, so nothing has to be quiesced for correctness: `hub_council_merge` returns false from the commit, and a job that names an old council (`dispatch.council`) and does not continue an interrupted one is refused at insert (`legacy-council-closed`), so an old door's `/council` fails in its own transaction instead of creating work no council tracks (a held seat's authorized recovery, reports and every ordinary write are untouched). The step takes the sheet lock and then the queue lock as its first statements and waits for the transactions in flight: an old settle that had read its sheet row finishes with its merge before the old councils are read, one that had not meets the sheet rows gone and returns. It may wait behind a long transaction of an old runner or door and it can be the victim of a deadlock with one; rerun it. Restart the doors on this build together with the runners (`imprnt hub install <registry> services <hub-entry>` renders units that carry it): an old door is not upgraded by anything here, and until it is, `/council` typed to it fails and is not converted to the new flow. No old binary needs to be run against a live store to prove any of this. (1) Apply migration 14 (`imprnt hub install <registry> database`, or the store's own migrate). It activates nothing, touches no row of live work, reads the old councils into the new tables and deletes the old council sheet rows; from that moment a council's job or event is refused to every claim that does not say protocol 3, so the old runners keep serving ordinary work. (2) Start the new runner on one machine. At start it passes `requireSchema` (a store before migration 14 is refused by name, before anything else), moves the store to protocol 3 once, then registers its incarnation and claims. Its activation is refused by name (`legacy-inputs-in-flight`) only when an input that a runner before protocol 2 may have fed is in flight, as before. From that moment every claim that does not say 3 is refused, ordinary rows included, and an older binary cannot register an incarnation. (3) Restart every other runner promptly: until it runs the new build it can neither claim nor register. An attempt it already has keeps running and settles, because neither settling nor releasing is a claim, and nothing is killed, discarded, replayed or settled by the activation. So: drain is about how long the other machines sit idle, not about losing work. To wait out a long attempt on another machine first, read `select runner, incarnation, protocol from runner_incarnation` and `select id, state, runner from execution where state in ('claimed','feed_intent','received','running','unknown','stop_requested','stop_unknown')` and restart that runner when it is empty or when that attempt is one you are content to have judged by the new runner's normal reconciliation. (4) Nothing moves back: the table refuses to lower the protocol, so after step 2 the old binaries cannot be put back in service against this store; a rollback is to run this build, or to restore the store, and either is a decision for the owner of the release and not a step.

A hunt entry (`kind = "watch"` with `source = "kleinanzeigen"`, `"mydealz"` or `"vstdeals"`) runs on a cadence such as `every 30m` and needs no credential. It reads its spec files from `specs` (default `<state_dir>/<person>/watch/specs/<source>/`, one `<id>.json` per hunt, the v2 shape byte for byte, `paused: true` to switch one off), posts every listing's audit row into the chat of the `audit` agent and appends the same rows to `<specs>/../../audit/<source>/<YYYY-MM-DD>.jsonl`, and hands triage hits to the `triage` master when the entry names one (an `[[agents]]` entry of the same person with `role = "triage"`, a door and a chat, whose chat is the audit channel, so ask it there why it ignored something). Run a tick by hand with the same `bun run src/entry/watch.ts <registry> <entry>`: exit 0 landed, exit 1 prints `watch-failed: <entry>: <cause>` and means every spec of the source was dark, a wall or a markup change, while one spec dark among several lands the rest and is one `spec failed` line in the audit. The state is the `watch:<entry>` sheet (one row per listing id) and the pending jobs are `watch-jobs:<entry>`. Deleting a listing's row makes the next tick treat it as new. `check` reports `watch-spec-refused` with the file's problems as the fix and `watch-triage-overdue` when a job has waited longer than the interval plus `hub.job_grace_seconds`.

A door whose registry names a `hub.cutover_batch` that is not complete yet waits instead of exiting. It serves and pulls nothing, and its diary and stderr carry one `start:cutover-incomplete` line naming the batch. It becomes ready by itself once the handoff completes that batch, so the unit needs no restart and no `reset-failed`.

Read failures and delivery failures retain their safe cause and route in state and diary. Failed install, start, and restart actions name their operation and target in the diary and service stderr. Child stderr inherits the service destination.

On Linux select the declared entry's journal with `journalctl --user --unit imprnt-hub-<entry>.service --no-pager`. Scheduled entries also have `imprnt-hub-<entry>.timer`. On macOS read `<state_dir>/service-log/<entry>.out.log` and `<state_dir>/service-log/<entry>.err.log`; the directory is private. Native checks query and remove only their own randomly suffixed fixture units.

## Topic chats

The owner can ask a master (General, or any chat's master) to make a new topic chat, and to archive and reopen one. This is the confirmed setup, the archive mirror, the missing-chat entry and the confirmed deletion (**Deleting a topic**, below). Moving a master to another machine is its own step. Only the deletion erases anything, and only after the owner's green check on its frozen scope.

**Settings, all optional, and nothing is guessed.** On a `[[people]]` entry: `topic_machine` (a declared machine) and `topic_preset` (a declared preset) are what a new chat is made with when the request names neither, and `general` names the agent whose chat is that person's General (their own agent, with a chat, not a seat or a triage master). On a Discord `[[run]]` door entry: `topic_machine` and `topic_preset` override the person's for chats made there, `topic_category` is the category new chats are made under, and `archive_category` with `archive_readonly_roles` is the archive: the category an archived chat moves into and the role ids that are denied writing in it while it is there (the bits are `SEND_MESSAGES`, `CREATE_PUBLIC_THREADS`, `CREATE_PRIVATE_THREADS` and `SEND_MESSAGES_IN_THREADS`; reactions stay). A category and role are Discord ids, digits only, and none of these keys is accepted on a Telegram door. `door.topic_poll_seconds` (default 30) is how often a door reads its server's channel list, once per door however many topics it serves. A request whose machine or preset resolves to nothing, to an unknown name, or to a machine with no runner the registry keeps running (or with two) is refused by name before any preview exists: there is no default machine.

**Making a chat.** The master calls `hub_topic create` with the owner's own message ids, the chat's name and the request. That freezes an exact preview in the chat where it was asked and creates nothing: `Chat`, `Execution machine`, `Agent` (engine and model), then the request exactly as it will be sent, and a requested tool profile after it. Both defaults are resolved and shown before the preview is hashed. A correction is another `create` with the topic id and the revision it replaces; the old preview can no longer be approved. Only the owner's green-check reaction on the last message of the preview that stands creates the chat, and there is no tool action, argument or field that confirms anything. The topic, its master agent id (`t-<uuid>`, never made from the chat's name) and its master conversation are allocated when the preview is frozen, so a chat that reuses a name has other identities. The door then asks Discord for the channel once, with an opaque marker in the channel description; the owner's request is stored as the new agent's first input in the same transaction that records the channel, with the chat's first read position at its very start, so nothing typed in the new chat while it was being set up is skipped. The hub then writes the agent into the registry, bound to the runner of the machine that was chosen, not to the machine the hub runs on. **What is bound is what was approved:** the person, the door, the chat, the machine and its runner, the preset and the engine and model it named when the preview was frozen, and the tool profile. The check is made by the registry writer on the very file its edit replaces (not on an earlier load), an entry of that agent id that is already there is accepted only if it is exactly what the bind would have written (that is a write that landed before the hub said so), and anything else is refused by code (`preset_changed`, `machine_changed`, `runner_not_running`, `binding_conflict`, `chat_taken` and so on) and left as it is. A refusal keeps the chat and the owner's first message, is said once in the chat where the setup was asked for, is retried every minute, and lets the same step finish as soon as what was approved is true again. A different setup is a new request and a new approval; nothing is substituted. A door that names no guild, or is not a Discord door, is refused before any preview is frozen, from the registry alone (no permission is probed).

**Starting is a milestone, not telemetry.** The new chat has one status line: `Waiting for <machine>` until something shows that the chosen machine's runner took the owner's first message up (it claimed it, or opened an attempt for it), and then, edited in the same message, `Started on <machine>`. A runner connected to the store is not that: a runner on another machine whose registry copy does not name the new agent is connected and claims nothing, so the line keeps waiting and `inspect` names why (`runner_offline`, `registry_not_synced` when the digests every hub writes do not show its copy to be the store machine's, `not_picked_up_yet`). Nothing follows the agent after that, and the line never claims it is running now. The store refuses to record a start for a chat that is not active, so a chat that was archived, is being reopened or is gone while its machine was away never says it started; a reopen lets the milestone through. The request waits for that machine alone, and nothing moves elsewhere.

**When Discord does not answer.** A channel creation has no idempotency key. If its answer is lost the door looks for a channel carrying the marker and uses it; a channel with the same name and no marker is not that chat. If nothing can be established the topic stays `creation_unknown`, machinery never creates another channel, and only the owner's decision does (`hub_topic create` with `creation_decision`: `adopt` a channel they name, or `recreate` once). A refusal (a bot without Manage Channels) names the step and is not repeated, and the owner can `adopt` a channel that is there for it too. An adoption is work the door owes from either state and wakes it by itself (each decision is a revision the store notifies the door of). The channel is read and checked against the platform (it exists and is a text channel), the topics (no other topic has it) and the registry (no agent already answers in it); one that fails is refused durably, by name and for that decision only (`topic-adopt-refused` in check, a notice, and `inspect`), with nothing created, and another decision is a new look. The topics and the registry are looked at again after the platform has answered and before anything is committed, because that answer can be slow and a binding may have landed meanwhile. That is a look and not a lock: the registry file and the topic table are different stores, so nothing makes the checks and the commit one step. What stands behind it is the store's one topic per chat of a door (a commit that lost that race fails, is reported and adopts nothing) and the hub's bind, which judges the chat as taken again on the file under the registry writer's own lock before it writes the agent. What the door read is committed only while that decision still stands, so a slow answer about one channel cannot win over a newer choice; one adoption makes one first input, one first read position and one binding, and never a request to create. Nothing is ever deleted by these steps. `imprnt hub check` reports `topic-creation-unknown`, `topic-create-failed`, `topic-bind-stuck` and, for an archive that is not finishing, `topic-transition-stuck` with what it is waiting for.

**Archive and reopen.** `hub_topic archive` and `reopen` are the owner's explicit request from that chat or from General, and need no second confirmation. Archiving gates the master's agent and asks for a stop of its running attempt in the same transaction, without waiting for a drain, moves the channel into the archive category and makes it read only for the named roles, and records exactly what it changed. The topic is `archiving` until the channel is read back showing it and no attempt of the master is owned any more: a stop that is not shown (`stop_unknown`, an offline machine) leaves it archiving, with the reason said once and a finding, and it is never called archived. Delegated work the owner already approved keeps running; its results wait and General is told once. Reopening puts back only what the archive changed and leaves anything somebody changed since, saying which; it releases the archive's own gate, so what waited is served, while an input that was interrupted stays held for the owner's own recovery choice (`/recover <agent> <attempt> <revision> continue|keep-held`) and nothing reruns by itself. Moving a chat into or out of the archive category by hand is the same operation; renaming it or editing its description or permissions is not. **Every ordinary master the registry names is a topic** (an agent of the door with a chat and no role: General included, workers and seats not), on a door that can list its server and names an archive mapping. The door links each one once, keeping the conversation it already has and refusing a retired identity, before it would park for want of topics and again whenever the set changes, so a master moved into the archive by hand is archived without anybody having asked through a tool. What was last seen of a chat's category is remembered only after the archive or reopen it asks for is recorded (a write that fails, a restart, or an answer of "not now" leaves the change to be seen again); a chat first seen outside the archive category is a baseline and nothing is reconstructed; one first seen inside it is archived from its current state, recorded as that (there is no earlier category, so none is made up, and a reopen leaves the category it cannot know and says so); and an archived chat that is not where its archive left it, including one moved out while the archive was still waiting for the stop, is reopened once the archive settles. It works the other way too: what an open operation does to the category is judged when it settles, from where the operation itself left the chat (its own record: the category the owner had put it in for a reopen made in Discord, the category the platform showed when the tool's reopen was applied), so a chat moved back INTO the archive category while a reopen was still open is archived once the reopen settles, through the same gate and stop, from that category. A reopen that could not know the chat's prior category leaves it inside the archive category on purpose, and being where the reopen left it is not a change, so it is not archived again by itself. A retired adopted master is not watched. **General is not special here:** it can be archived and reopened like any other master, by moving its channel out of the archive category, with no turn of its model. The notice goes where the request was made, or to General when that chat is the one archived, and only where a chat can take it: General is checked as a chat (not archived, being reopened or gone), independently of whether its agent can run, so a General whose model is held still receives the door's line. A notice and what is recorded of whether it was told are written in one transaction, so a gap is never cleared for a notice that was not queued and a queued notice is never left beside a gap that says it could not be told. When neither can, nothing is queued as told; the reason is kept on the topic (`inspect` says it, and `check` reports `topic-attention-unavailable`, and `general-unusable` for a configured General that is archived or gone). With no General configured it is kept on the operation and `check` says `general-not-configured`.

**A chat that disappears.** When a complete channel listing lacks the chat and a read of it by id names it as gone, the topic is `channel_missing`, its master takes no new work and one keyed notice asks in General. Nothing is erased, and the notice says that deleting the agent and its history is the owner's own request to make and confirm (`hub_topic delete`), and that nothing is erased before they confirm. A refused read, a server error, a rate limit or a failed listing is not a deletion: it only records when the chat was last looked at. An adopted master (a legacy topic) whose chat vanished while it was **active** is repaired the way it always was, with `/agent adopt` onto a chat: the registry is edited first, then the topic follows, keeping its identity, conversation and history; only its own missing-channel gate is released (a hold, or another operation's gate, stays), and the pending deletion request the disappearance made is closed as superseded by the repair. One that vanished while it was being archived, archived or being reopened is refused by name and stays gated: its archive belongs to the old chat and is never applied to another. An active adopted master can also still be retired and adopted again as itself (same identity, conversation, preset and runner); a master the Hub made, or one that is archived or gone, is not retired or adopted by hand. **Every disappearance is an operation of its own.** It is named after the topic and the lifecycle generation it begins at (`missing:<topic>:<generation>`, kept on the topic while the chat is gone), and its gate, its pending deletion request (`deletion-request:<topic>:<generation>`) and its notice (`topic:missing:<topic>:<generation>`) all carry that name. A repair releases and closes only that disappearance; if the repaired chat vanishes again it is a new operation with a gate, a request and a notice of its own (a released gate is never placed again, so a second disappearance could not reuse the first's), and the first stays released, closed and told. The same disappearance found again, after a restart or by a look that was already on its way, is the same operation and makes nothing more.

**An adopted master follows its registry entry.** The door looks an adopted master up by its agent across doors. When its entry was edited onto another chat or another door (or removed and added again by hand), the ACTIVE topic is moved onto the route the registry now says: the same topic, agent, conversation and history, never a second topic, and what was seen of the old chat goes with it, so the new chat is looked at as a first sight. This moves where the master is *watched*; it is not a way to move where it executes. Only the full eligible binding is watched (same person, an ordinary master of that door with that chat, not retired), so the old channel, deleted or moved into the archive category, is nothing to it. A master that vanished while active is brought back only by a genuinely changed, validated binding, never because the same agent id reappeared on the route it vanished from. One that is archiving, archived or being reopened, or vanished from its archive, keeps its archive, its gates and its history: nothing is moved, nothing is watched on the new route, and `imprnt hub check` reports `topic-binding-mismatch` (and the door's diary names `topic-binding-mismatch`) until the entry is put back on the route the topic has, or the chat is reopened first. A retired topic, agent or conversation identity is never moved, even for a topic that is already linked, and another person's agent is never given the topic. A read of a channel that took time is judged again against the binding as it stands before anything is written from it, and every write about a chat names the route and lifecycle generation it looked at, so an old channel's 404 or archive that arrives after a repair cannot gate or archive the replacement.

**What could not be told is caught up with.** A notice that had nowhere to go leaves a numbered gap on its topic. On every pass, whatever else the door has to watch (a chat that is gone is not watched, and its gap is the very one this pays), the door looks for gaps and, when the topic's own place (where it was asked for) or General can take a notice, queues ONE keyed catch-up notice (`topic:attention-catchup:<topic>:<kind>.<occurrence>,...`) that names what was missed and where the chat stands now, and clears exactly those gaps in the same transaction; a gap that opened after they were read is left for its own catch-up. It says it is a summary that is queued now and never that the original was told, it asks nothing that was settled since, and delivery is the outbox's as always; it gives no agent an input. A failed write keeps the gaps. The task stays due at the retry interval only while a gap could be paid by a change of state (General is archived, and reopens); a gap only the registry can pay (no General configured) is woken by the registry change the door already hears, and nothing polls for it. A council's need that no chat could take is kept in the same map and paid by the same pass, toward the chat the council answers in (see the release limits of councils and topics together).

**Retired identities.** A topic id, agent id or conversation id can be written into `identity_reservation` (`hub_identity_reserve`); it can never be changed or removed, and from then on the store refuses that agent id a conversation or a message, `/agent adopt` refuses it, a legacy master with that id is never linked as a topic, and `check` reports `reserved-identity-in-registry` if the registry still names it. A confirmed topic deletion writes the reservations (the topic, the agent and every conversation it owned) before it erases anything.

**Deleting a topic (migration 017).** `hub_topic delete` is the owner's explicit request, from the topic's own chat or from General, and it deletes nothing: it works out the scope (counts of what would be removed, never a word of the history; the machines that may hold copies; the retention that is configured, or that none is) and freezes it as a preview, which is the only thing the owner's green check can confirm. Asking again replaces a preview nobody approved. The check commits, in the approval's own transaction, the reservation of the topic, agent and conversation ids (so they are never used again), a content-free tombstone, one receipt for every location a copy was recorded at, a gate on the agent, its delegated conversations and its queued jobs, and a stop request for what they own; the topic is `deleting` and archive, reopen and move are refused for it. **Nothing is erased while the agent or a delegated conversation still owns an attempt that nobody has shown gone.** Then the door asks the store for the removal, one transaction, children first: inputs, replies, attachment bytes, conversation entries, attempts and holds, councils and the proposals its agent made (they carry the question and the context), moves, the topic's state sheets (a closed list, `src/erasure/inventory.ts`: `agent_wait`, `agent_health`, `harvest`, `door_cursor`, `door_health`, `move_command`, `move_command_done`, `turn_progress`, `door_progress`, `control` and `sender_denied`; every other sheet the source writes is classified there as not a topic's, and a test fails on a sheet nobody classified), the Hub's own messages about it and, through the one narrow path the diary's append-only fence allows (only for a confirmed deletion's tombstone, never for a runner or the model's login), its diary rows. The door then deletes the platform chat and the Hub's own previews posted elsewhere, recording what Discord said for each (`gone` is Discord's word; a refusal is `blocked`; a platform with no delete verb is `unsupported`, never credited), and each machine's hub removes its own chat log, attachments, session files, the notes staged for the vault (`<state>/<person>/harvest/harvest-<agent>-<until>`, by this agent's name only: the filed note is the vault's and is never touched) and its movement copies, and reports each (`erasure_receipt`). **A movement copy's location is the one the movement manifest (migration 016) gives**: `<state>/<person>/sessions/<agent>/<conversation>` on the copy's machine, for the destination's staged import and the source's retained session alike. The paths the copy's own evidence recorded (its `promote_intent` session directory and its stage receipt's destination) are kept on the receipt and checked against it; a copy that recorded another place is `blocked` by name (`movement_copy_path_differs`), nothing is removed at that place, and the deletion stays `blocked_scope` with that copy named. A machine that is off is waited for: the deletion is `pending_machine` and says so, and is complete (`active_deleted`) only when every inventoried active copy has a receipt that says erased. A copy that cannot be erased leaves it `blocked_scope`, with the copy named. **Independent vault knowledge is not touched, and no deletion cascades into it.** Earlier backup copies are not rewritten.

**Backup retention.** `hub.backup_retention_days` is the owner's number of days a historical backup copy may remain, counted from the copy's own creation. It is not in the shipped registry and has no default: with it absent every deletion says that no retention is configured (30 days was a proposal and is applied nowhere). Each backup copy's `manifest.json` records the erasure generation it was assembled under and, when a retention is configured, `expires_at`. **What the destination can do is declared, not assumed.** A backup entry that declares only `dump_argv`, `upload_argv` and `readback_argv` (every entry that exists today) cannot list or remove a copy, so expiry cannot be verified or carried out through it: a deletion with a configured retention reports `retention_unverified` with that reason, the earlier copies remain until removed by hand, and nothing is ever reported expired. An entry that also declares `list_argv` and `expire_argv`, with an upload and a read-back that carry `{generation}`, gives every copy a place of its own at the destination and can be enumerated and expired by the job itself. `{generation}` is the copy's id, the UTC second it was assembled (`20261001T120000Z`), and is the only value ever filled into the expiry command: ids the destination lists that are not of that shape are not copies of this job's and are never touched. The loader refuses half a policy (one command without the other, an expiry that names no copy, a place of its own in the upload and not in the read-back). Example, for a destination that is a directory on another disk:

```toml
upload_argv   = ["/bin/cp", "-R", "-f", "{staging}/.", "{destination}/{generation}"]
readback_argv = ["/bin/cp", "{destination}/{generation}/{path}", "{out}"]
list_argv     = ["/bin/ls", "{destination}"]
expire_argv   = ["/bin/rm", "-rf", "{destination}/{generation}"]
```

With a generation layout the copy is assembled in `<staging>/generation` with a standalone dump (no repository, so no earlier dump's history is carried in every copy) and that directory is what the upload is handed as `{staging}`; the legacy dump repository in the staging directory is never sent again. **What the job does with it, after every run, whether the fresh copy landed or was held:** list the destination; read each copy's own `manifest.json` back for its creation time and erasure generation; remove, one at a time, the copies older than `hub.backup_retention_days` counted from that creation (there is no exemption for the newest or the last good copy, so a failed fresh backup is reported and keeps no old history); list again, and call a copy `expired` only when it is no longer listed. A copy whose manifest cannot be read has no age and is `retention_unverified`; one the destination did not remove is `retention_blocked`, with the reason in the diary (`backup-retention`). A copy is history of a deletion when it was assembled under an earlier erasure generation than the deletion's (or before generations existed, or its age is unknown); each such copy is a receipt of the deletion, the latest expiry among them is `backup_retention_until`, and `historical_copies_expired` is recorded only when every one of them is shown gone (the store refuses the word otherwise). A deletion for which no earlier copy is found stays `tracking` and says so; it is never `historical_copies_expired` from an empty listing. **Limits, stated plainly:** the copy a destination already holds in the old single-directory layout is not a generation, is never enumerated, and has to be removed by hand (or moved under a generation id with a manifest, which then ages by that manifest); the layout is one copy per run, so an hourly schedule keeps one copy per hour: choose a daily schedule, or a destination that deduplicates, before turning it on, because a destination that stores each copy whole holds as many whole trees as there are copies in the retention window (this was not measured on the household's transport); local provider versioning, WAL archives and file-system snapshots are not enumerated or expired by this job and are the household's to bound. `check` says what remains (`backup-retention-unverified`, `backup-retention-blocked`, `backup-retention-not-configured`). A copy is never assembled across an erasure generation, or while a confirmed deletion's rows or this machine's copies are still to be removed: the backup is held with that reason and the next run assembles it from what is left.

**Restore barrier.** Every hub keeps `<state_dir>/erasure-manifest.json` current (identifiers only, merged so it only grows) and every backup copy carries the same file. **The restore procedure has one more step, between the restored database and starting anything:** with no door, runner, sync or hub running, restore the database, run the install step's database stage (it applies migration 017), then `imprnt hub restore <registry> <machine> [--from <state dir>]... [--snapshot <copy dir>]`. `--from` names the state directory of every other machine (or a newer backup copy) whose manifest is a source of what was deleted since the copy was made, and `--snapshot` the backup copy that was restored. The command merges every source into the restored store, which reserves the deleted identities again and erases whatever of those topics the old copy held; removes this machine's restored chat logs, sessions, staged notes and attachments of them by identifier; removes, on the store machine, a registry entry that still declares a deleted agent; and exits 0 only when nothing of a deleted topic can be served from here. It exits 1, and starts nothing, when no manifest source can be read (a deletion may have happened since the copy was made and the copy cannot say), when the snapshot's own manifest is torn, when a registry binding cannot be removed or a restored file cannot be, or when the store is not at schema 17. **After that the hub reconciles on its own** (`src/erasure/startup.ts`): on every tick, before it installs, starts or restarts anything, it shows that the store holds every deletion this machine's copy of the manifest records, applies the ones it lacks, cleans a registry that still names a deleted agent (the store machine's hub only; a spoke holds until its copy is replaced), and, once after each start, sweeps this machine's disk for what a restore brought back. It holds the machine, and says why once in the diary (`erasure-hold`), only for an explicit answer (the store cannot be brought forward, the registry cannot be cleaned); a failure of the check itself is said (`erasure-reconcile`) and does not stop the machine. A door or a runner the manager restarts on its own refuses to start against a store that lacks a deletion this machine recorded (`erasure-behind`); the hub brings the store forward and the manager starts it again. A manifest, this store's own included, never erases a deletion that is still stopping its agent: that deletion's own routine erases it after the stops are shown. **What it cannot know:** a deletion that no manifest anywhere holds (confirmed after the newest copy, on a machine lost with its store). **Rollout order:** migrate the store first (a runner of this build refuses a store without migration 017 by name, `schema-behind: apply migration 17`), then the hubs, then the doors and runners; against a store not yet migrated a hub, door or backup of this build degrades to "nothing was deleted here", the `delete` action refuses with `schema_not_ready`, and a machine whose own manifest names a deletion holds until the store is migrated.

Migration 015 follows the councils' migration 014 and adds the topic tables, the reservation and two `BEFORE INSERT` fences (on `conversation` and, except for a worker's report, on `inbound`); it replaces nothing 014 replaces, so a store at 014 takes it as it is. Apply migrations 014 and 015, in that order, before starting a door, hub or runner of this version (`imprnt hub install <registry> database`, or the store's own migrate, applies whatever is missing).

**Release limits of councils and topics together.** These are what this build does, not decisions of the owner, and nothing here adds behaviour. (1) A council notice goes to the council's own chat and to the person's General as the registry names them, and only to a chat that can take it, measured as the topics measure it (not archived, being reopened, gone or being deleted; whether the agent behind it can run is not asked). With the council's chat archived or gone and General usable, the owner is told in General and nothing is written to the archived chat; with General unusable and the council's chat usable, that chat is told. **A need no chat could take is kept and caught up with.** That is both unusable, no General configured and the chat unusable, a need that is the chat's alone (a quiet or long-running worker) with the chat unusable, or the failed-card diagnostic, which is General's alone, with General unusable (with no General configured that diagnostic is not kept: `check` already says `general-not-configured`). It is kept on the topic of the council's chat, in the attention map a topic's own missed notices use (`hub_topic inspect` shows it and `check` reports `topic-attention-unavailable`, under a `council-<need>-…` kind), and the topic catch-up above pays it once, in the same pass that finds a place: ONE keyed summary (`topic:attention-catchup:<topic>:council-…`) that says a council needed the owner, what, and where the chat stands now, queued in the council's chat when it can take it again (a reopen on its own delivers nothing; the catch-up does) and otherwise in General. It is a summary and not the original notice, and not a continuation of the council: it gives no agent an input, no other master speaks for the council, and the council's results and the master's turns are neither reordered nor replayed. A need that was said, or caught up with, is never kept or said again however often it is looked at and whatever restarts; a need that opens while another is being caught up with is an occurrence of its own and is left for its own summary. A gap whose council was erased, or whose topic is being deleted, is cleared without a notice. A council that answers in a chat that is not a topic has nothing to measure and is written to as before, and keeps nothing. The card (the one edited message) is not asked to edit in a chat known not to take it; its words are written once it can. **Limits:** the summary names a need as it stood and does not check that it was settled meanwhile; a General that could not take a need said in a usable chat is not told of it later, and a need already told in General is not told in a chat that is reopened afterwards; the `topic-attention-unavailable` finding shows the kind as recorded, not in words. `general-unusable` in `check` still names a General topic that is archived or gone, on a door that check covers. (2) The generic delivery-failure diagnostic, which names an agent and a cause and may be sent to another chat of the person when a route fails for good, does not forward a council's notice, content or results: it is never a fallback for them. (3) Start the combined services only after migration 015 is verified applied (`select max(version) from schema_version` shows 15). The runner's start-up schema check requires the council objects of migration 014 and nothing of 015, so a runner on a store at 014 starts and fails when a topic operation first needs 015; it is not proof that the whole combined schema is present. The limits already stated for topic attention and for a claimed attempt are unchanged.

## A runner on another machine

The Pi stays the hub, the record and the only door. A second machine, the owner's Mac, runs one runner, one hub and one sync of its own, controlled from the Pi's registry, and serves the agents bound to that runner: it reads their chat out of the one store, answers into it, and files notes into the vault checkout on its own disk, which its sync pushes to the same remote the Pi pulls from. An attachment a person sends is saved by the Pi's door under the Pi's state directory and written into the store in the same transaction, and the Mac's runner writes it into its own person inbox, checks the hash, and feeds the row and the tail with its own path. The registry is one file for every machine. The `[hub]` table and the entries' own paths are the Pi's, and everything that differs on the Mac is said beside them: the machine's `state_dir`, `secrets_dir`, `store_url` and `imprnt` on its `[[machines]]` entry, each person's tree, vault and instruction files there under `on.<machine>`, each credential's file there under its own `on.<machine>`, and each repository's checkout, remote and `ssh_command` there under its own (the Pi's ssh command never follows a checkout, and an empty string means the account's own ssh). Every process reads the file for its own machine (`check`, `status`, `metrics` and `recover` take the machine as an argument), so the same bytes serve both. A person's or an agent's instruction files are checked readable only on the machine their runner is on. `hub.store_machine` names the Pi as the machine whose copy is the one: every hub writes the digest of the copy it runs on to the `registry` sheet on its tick, the Mac's runner compares its own copy with the Pi's before it claims anything and claims nothing while they differ or while the Pi's hub has not written its row, and `check` on the Pi reports `registry-stale` for a copy that differs and `registry-unseen` for a machine whose hub has not written in the job grace, and sweeps the overdue chats of the agents on such a machine as its own. Machine ids, addresses and paths below are examples: use the household's own.

1. On the Pi, let Postgres listen on the tailnet address beside loopback. As the database administrator: `sudo -u postgres psql -c "alter system set listen_addresses = 'localhost,<the Pi's tailnet address>';"`. The setting takes effect at the restart in step 3.
2. On the Pi, admit the four hub roles from the tailnet, with a password and nothing weaker, by adding one line to `pg_hba.conf` (`sudo -u postgres psql -Atc "show hba_file"` says where it is), after the existing loopback lines: `host hub hub_door,hub_runner,hub_agent,hub_hub 100.64.0.0/10 scram-sha-256`. The range is the whole tailnet, and only a machine holding a role's password file gets in.
3. On the Pi, restart the store and see it listen: `sudo systemctl restart postgresql@15-main`, then `ss -ltn | grep 5432` shows both addresses. `sudo -u postgres psql -Atc "select line_number, error from pg_hba_file_rules where error is not null"` prints nothing when the new line parsed.
4. In the registry, describe the Mac. In the `[hub]` table add `store_machine = "pi"`. On the Mac's `[[machines]]` entry add `state_dir = "/Users/<owner>/.imprnt-hub"`, `store_url = "postgres://<the Pi's tailnet address>:5432/hub"` (no user and no password in it) and `imprnt = "imprnt"` when the Pi's `hub.imprnt` is a path the Mac does not have (a bare word resolves through the unit's PATH, which carries `~/.local/bin`, `~/.bun/bin` and `/opt/homebrew/bin`). Add a `[[run]]` entry `runner-mac` of kind `runner` with `machine = "mac"` and `child_memory_limit_mb`, a `[[run]]` entry `hub-mac` of kind `hub` with `machine = "mac"`, and a `[[run]]` entry `vault-sync-mac` of kind `sync` with `machine = "mac"` listing the owner's vault repository. On the owner's `[[people]]` entry add `on = { mac = { tree = "/Users/<owner>/imprint-vault", vault = "/Users/<owner>/imprint-vault" } }`: the tree is the box's fence on the Mac, and the vault lies inside it. On the owner's vault `[[repositories]]` entry add `on = { mac = { path = "/Users/<owner>/imprint-vault", ssh_command = "" } }` (or the Mac's own `ssh -i` when the remote wants a key of its own there). On the `claude-login` credential add `on = { mac = { file = "/Users/<owner>/.imprnt-hub/login/.credentials.json" } }`. Bind an agent to the Mac with `runner = "runner-mac"` on its `[[agents]]` entry; its door stays on the Pi. A person's `filing_rules`, `instructions`, `mcp` and `settings`, and an agent's `fragment`, `settings` and `mcp`, are checked readable only on the machine the agent's runner is on, and a person's may be placed under `on.mac` too when the Mac keeps them elsewhere.
5. On the Mac, install the CLI the runner files notes with and the hub it dispatches to: `npm i -g imprnt` (or `npm link` from `packages/imprnt` of the checkout), so that `imprnt` is on the unit PATH above (`which imprnt` prints a path under `/opt/homebrew/bin`, `~/.local/bin` or `~/.bun/bin`; anywhere else, put a link in `~/.local/bin`). `imprnt hub` dispatches to the hub plugin under the selected vault, so link it there: `ln -s ~/IdeaProjects/imprnt/packages/plugin-hub ~/imprint-vault/plugins/hub`, with the repository at that path and `bun install` done, and `bun` at `~/.bun/bin/bun` and `claude` at `~/.local/bin/claude`. The vault checkout at the tree named in step 4 needs the ssh key its remote wants on the account. Make the state directory with `mkdir -m 700 -p ~/.imprnt-hub/secrets`, then copy the two role passwords from the Pi's secrets directory: `scp pi:/var/lib/imprnt-hub/secrets/hub_runner.password pi:/var/lib/imprnt-hub/secrets/hub_hub.password ~/.imprnt-hub/secrets/` and `chmod 600 ~/.imprnt-hub/secrets/*.password`. Copy the registry to the Mac at a path of its own, and copy it again after every edit: the Mac's hub re-reads its copy on its tick, and until the copy matches the Pi's byte for byte the Mac's runner claims nothing and `check` on either machine says `registry-stale`.
6. On the Mac, log the runner in, once: `CLAUDE_CONFIG_DIR=~/.imprnt-hub/login/config CLAUDE_SECURESTORAGE_CONFIG_DIR=~/.imprnt-hub/login claude auth login`. It opens the browser, the owner approves, and the CLI writes `~/.imprnt-hub/login/.credentials.json`, which is the file step 4 names. This is a login of its own for the runner, a second device on the account. It is never the owner's own login and never a copy of the keychain item: a refresh token is single use, and a copy that refreshes revokes the login it was copied from, which was measured on the owner's Mac by losing the owner's login. Nothing in the hub reads or writes the keychain.
7. On the Mac, `imprnt hub check <registry> mac`. It opens the store over the tailnet as `hub_hub` with the password from step 5, opens the runner's login file and judges the login in it, and reports the tree and the vault when they are not where step 4 says. Until step 6 has been done it reports the login `credential-unreadable` with step 6's command as the fix.
8. On the Mac, `imprnt hub install <registry> services hub-mac`. It writes `~/Library/LaunchAgents/imprnt-hub-hub-mac.plist`, `imprnt-hub-runner-mac.plist` and `imprnt-hub-vault-sync-mac.plist` with the Mac's own log directory under `~/.imprnt-hub/service-log`, bootstraps them into the login session and starts the residents. Only the Mac's entries are written: the Pi's door, sync, board and backup are left to the Pi. `imprnt hub status <registry> mac` shows the residents running, and the store's client list on the Pi shows `runner-mac` connected from the tailnet address.
9. Send one real message in the bound agent's chat and read the answer. The Pi's door writes the row, the Mac's runner claims it, answers it and settles it, the Pi's door posts the reply. Then say `harvest this` in that chat: the Mac's runner reads the slice out of the store, the note lands in the vault checkout on the Mac, and the Mac's sync pushes it within its cadence.

The units are login agents: they run while the owner is logged in, a locked screen is fine, and nothing runs before login, which is what launchd offers. The boxed loop reads the runner's login file under `CLAUDE_SECURESTORAGE_CONFIG_DIR` exactly as it does on Linux, and a box cannot read the owner's keychain at all (measured: `security find-generic-password` inside a session box finds nothing and cannot list `~/Library/Keychains`). The whole state directory, the login file included, is private to the account, and every agent's box masks the secrets directory and every credential file but the one its own loop runs on.


### Deletion: what is done, and what is not (IMP-232)

**Implemented, with a regression test for each (listed below; they were written without a shell and had not been run when this was written, so run them before relying on any of it):** the confirmed, frozen scope; the stop-first rule; the scoped erasure of every inventoried row and the narrow ledger path; the platform deletion with `unsupported` and `blocked` never credited; per-machine receipts and `pending_machine`; the permanent reservation of identities; the restore command, the hub's startup reconciliation and the start fence of doors and runners; the schema fence; the generation layout and the finite retention transport (`list_argv`, `expire_argv`), enumerated, aged, expired and verified by the job; the backup barrier.

**Not done, and not claimed:** (1) no retention duration is owner-approved: `hub.backup_retention_days` has no default and nothing expires until the owner sets it; 30 days is an engineering proposal named in code and applied nowhere. (2) The household's actual backup destination has not been inspected (no private or live transport was touched), so whether it can list and expire, and what its copies cost in storage, is open: until its entry declares `list_argv` and `expire_argv` every deletion reports `retention_unverified`. (3) The legacy single-directory copy at a destination, local provider versioning, WAL archives and file-system snapshots are not enumerated or expired. (4) Chat labels are kept in `topic_deletion.evidence` and in the notices posted in General so the owner is told which chat; the tombstone and the manifest hold none. (5) Receipts record locations the Hub itself recorded: no text scan proves a model never copied something elsewhere, and none is pretended. (6) `imprnt hub restore` and the reconciliation are tested against a throwaway store and a fake Discord, never against a live restore. No live deletion or backup has been performed.

**Tests** (from `packages/plugin-hub`, with `BUN_FEATURE_FLAG_DISABLE_SQL_AUTO_PIPELINING=1`; they start a throwaway Postgres cluster and need no network): `test/topic-deletion.test.ts`, `test/topic-deletion-restore.test.ts`, `test/topic-deletion-startup.test.ts`, `test/topic-deletion-inventory.test.ts`, `test/topic-deletion-retention.test.ts`, `test/erasure-retention.test.ts`, `test/backup-registry.test.ts`, and `test/backup-erasure.test.ts` (needs `pg_dump` beside the cluster's binaries; the checks that need a copy to land also need a second device and skip with the reason in their name).

## The OpenCode engine

Chinese and API models run through OpenCode (`adapter = "opencode"`); Claude stays on Claude Code, unchanged, and nothing here moves a Claude conversation. The hub writes no model loop and no tool loop: it runs the engine's own server, one process per conversation, in its own box and session directory, and speaks to it over the server's HTTP and event API (`src/adapters/opencode*.ts`). **Nothing here is activated.** No provider, account, model or key has been chosen and no preset names the engine. The code was checked against the pinned v1.18.34 OpenAPI document and against a scripted stand-in for the server; the real engine has only been started and resumed through the adapter with a placeholder key and no model call, so no turn, tool call, usage figure or provider answer has been seen.

**Activating it is the owner's, in this order.** (1) Install the pinned build on the machine that will run it and say which one: the pinned release is v1.18.34. (2) Run `live/prove-opencode.ts` against that binary (no model call, no real key): it reads back the restrictions, creates, stops and resumes a session in a throwaway directory, and prints what it saw. (3) A build is listed in `VALIDATED` in `src/adapters/opencode.ts` only for what was measured on it, with the observation beside it. v1.18.34 is listed for its session store and for the configuration read back from the running server (`task` deny, depth 0, no listed subagent); it is not listed for safe resume. A build that is not listed has the capability false: the runner starts no session under a stable id, and an ordinary launch is refused by name (`native-tool-control-unvalidated: opencode <version>`). (4) Choose the provider, the model and the account, write the key to a file of its own (the token and nothing else), declare it as a `[[credentials]]` entry of kind `model-key` (see `registry.example.toml`), and declare a preset with `adapter = "opencode"`, `provider` the engine's own provider id, `model` the model id under it, `paid = "key"` and `credential` naming the entry. A preset is used by naming it: no door's or person's default is changed by any of this.

**What a launch is.** The key is read by the runner outside the box and handed to the engine as one environment variable; the inline configuration names that variable and never holds the key; the key file stays masked from the agent. The engine's home, its XDG directories (so its sessions, its credentials file and its configuration) and its scratch are inside the conversation's session directory; nothing is inherited from the parent but `PATH`, `LANG`, `LC_ALL` and `TZ`, so no ambient provider key, config path, plugin or experimental switch reaches it, and the engine's reading of `.claude` is switched off. The server listens on loopback on a port the adapter picked, behind a password of its own per launch, and a server that does not refuse a wrong password is not the one that was started. The configuration pins one provider (`enabled_providers`), one model, and the same model for every auxiliary use (titles, summaries, compaction), because the engine's default there is a cheaper model from wherever one is available. Permissions are deny by default and name exactly the agent's tools; `external_directory`, `doom_loop` and `question` are all answered, so no headless session waits to be asked. The person's MCP servers are translated into the engine's spelling and the hub's own tool server is added beside them; a shape the translation does not know, and any permission rule in the person's settings (Claude's rule language has no deterministic translation), is refused by name.

**Delegation.** The engine's own subagents are off four ways: the `task` permission, a subagent depth of zero, each built-in subagent disabled by name, and the legacy `tools` switch. The adapter then reads the effective configuration back from the running server and refuses to start on a server that does not hold it, and a child session or a permission request during a turn stops the turn as a refusal. That is the whole claim, and it is a claim about the configuration as the running server reports it: on v1.18.34 `GET /experimental/tool/ids` still lists `task` (that is the tool registry, not the effective permissions), and nobody has had a model attempt a task call, so a refused call is not shown. It does not stop a shell from calling a model API, and a configuration the pinned release merges, renames or reports in a shape the adapter cannot read is refused, never waved through.

**Turns.** One prompt is posted, once, under a message id the hub chose (`messageID`, which the spec's prompt body accepts). The engine's own echo of that message on the event stream is the receipt, and the same text recorded under any other id ends the turn as an error and never as a receipt; assistant text (from `message.part.delta`, attributed through the part the engine named) and tool starts and results are progress (a tool's output never leaves the adapter); the turn ends on the engine going idle, and the answer is read from the engine's record of its messages. Usage is the engine's; a count it did not report is unknown, and zero in with zero out is read as unreported. A post that fails after it began is uncertain (only `FeedNotWritten` says nothing was written, and only before the first byte); a lost event stream ends the session as exited; nothing is posted again. An answer from another provider or model than the bound one refuses the turn. A refusal is typed: a provider 401, or the engine's own `ProviderAuthError`, is `login`; a 429 or quota words are `window`; anything else is `other`. Only a provider's own 401 is evidence that opens a credential outage, and a key per token has no window.

**Sessions.** The hub's session id is mapped to the engine's own in `opencode/hub-session.json` beside the engine's data, with the identity it is bound to (engine, provider, model, endpoint). A resume of an id that map does not hold, or holds under another identity, or whose session the engine no longer has, is refused by name (`opencode-session-unknown`, `opencode-identity-mismatch`, `opencode-session-missing`) and a fresh session is never made in its place. A conversation of this engine does not move between machines: the adapter has no native session port, and nobody measured that the engine's database resumes elsewhere. An existing Claude conversation rebound to an OpenCode preset is refused at launch by the same rule, each time, until the owner chooses; no owner-approved recovery action exists yet.

**Stop.** The engine is asked to abort the session, given a moment to settle, and the process tree is ended and judged by the process table exactly as the Claude adapter's is. What an aborted turn left in files or APIs is not undone, and `safeResume` is false until a build is measured to replay no unfinished tool call.

**Effort.** `default` sends no variant. Any other effort is sent as the `variant` of the same name, and only when the running engine lists that variant for the model (`GET /provider`); otherwise the start is refused by name (`opencode-effort-unsupported`, listing the model's variants) before any session is made. There is no translation table. If the engine records another variant than the one asked for, the turn is refused and its text is not posted.

**Known gaps.** `check` reports an unusable OpenCode binary as `credential-source-unsupported`. The key is in the environment of the engine's tools, so an agent's shell can read it, as it can read the login file of a Claude launch. The open questions about the engine's API are listed in the result file of the change that added this.

Deletion publication and restore safeguards: backup holds a dedicated shared maintenance lock from its final erasure check through publication/read-back; confirmation and erasure take the matching exclusive lock. Failed local purges continue to hold backups. An unreadable local erasure manifest is preserved and blocks startup until independently recovered. Tombstones carry worker agent/conversation paths so a disk restore removes only the deleted worker sessions. Retention may expire recognized generations, but its overall status remains unverified until legacy dump history and retained destination versions are inventoried; generation removal alone never certifies all historical copies erased.

## Coordinating sync writers

A sync entry holds a PostgreSQL session advisory lock before reading its previous result and until its new result and notices commit. A contending tick of the same entry skips without writing a result or refreshing success. Repository locks use the existing `sync:<machine>:<canonical common Git directory>` key, shared with Hub movement; those locks now remain held through result publication too. PostgreSQL releases them when their owning session closes, including process exit. No new filesystem lock file or stale-lock removal convention is introduced.

These locks coordinate participating Hub operations. They do **not** exclude a shell, editor, agent, or legacy publisher that ignores the protocol. An unrelated `flock` would not make Git obey it either. Retire duplicate Git publishers, or have their Git work run through the same Hub synchronization/locking protocol; do not give a second timer independent add/commit/pull/push authority over the live checkout. Ordinary note writing remains allowed, but changes made during an in-place Git operation can still race with it. The checks below narrow and detect races; they are not a transaction over arbitrary filesystem writers.

Before mutations, sync rechecks the configured branch, expected HEAD, and incomplete operation/unmerged state. A changed branch/revision or pending merge/rebase/sequencer is refused and left in place. After a sync commit its parent must be the checked HEAD. Rebase uses the captured fetched commit id, never a later writer's shared FETCH_HEAD. Branch/HEAD/operation checks run again before every push, around the tracking-ref compare-and-swap, and before success is recorded. A detected late change can mean some destinations already received the pinned commit; sync reports failure rather than claiming a complete run.

Normal sync still commits pending notes and rebases a clean eligible checkout. It does not automatically continue, abort, quit, retry, reset, clean, drop a stash, or resolve a failed operation. Before manual repair, stop competing Git writers and preserve pending files, index state, refs and stashes. Inspect the existing operation and decide its recovery explicitly. Never use a destructive reset merely to silence a sync failure.

A failure streak is timed from its first recorded failure. The first failing run at or after thirty minutes queues one plain-language notice to the person's resident chat (or first eligible chat), naming the current condition and preservation advice. The notice and durable `notified_at` marker commit together, so later runs do not repeat it even if old outbox rows are retained for less time. A successful run clears the streak; a new prolonged failure can then produce a new notice. A person with no eligible chat route still has the sync finding, and remains eligible for the notice if a route becomes available. This measures repeated completed failures: a permanently hung Git process cannot publish a new outcome, so this threshold alone is not a watchdog for hung processes.
