# Codex worker adapter

`adapter = "codex"` uses Codex App Server's existing agent engine through the shared Hub adapter interface. Jobs keep their own Hub conversation and explicit follow-ups resume its mapped Codex thread. Progress, final answers, usage, receipts and explicit stops use the normal runner lifecycle; Hub does not implement another model/tool loop.

The protocol is bound to CLI `0.160.0`, with the installed build checked before preparation and again at initialization. Official references: [App Server](https://learn.chatgpt.com/docs/app-server), [configuration](https://learn.chatgpt.com/docs/config-file/config-reference), [feature flags](https://learn.chatgpt.com/docs/config-file/config-basic), and [MCP](https://learn.chatgpt.com/docs/extend/mcp). The generated schema and real local binary establish the exact wire spellings; examples on the website may describe a different build.

Use an explicit preset model, provider, effort and `model-key` credential (`paid = "key"`). `openai` defaults to `https://api.openai.com/v1`; another provider needs its explicit Responses-compatible `base_url`. This adapter does not import a ChatGPT login, change a global account, or infer a model. Model/provider mismatches fail. After verifying `cli_auth_credentials_store = "ephemeral"`, the runner supplies the key through App Server's private `account/login/start` RPC. The process keeps it in memory only; every restart authenticates anew. No key enters argv, the process environment, generated config, model input or an auth file. The configured credential file remains masked by the existing Hub box. This uses the documented [App Server API-key authentication](https://learn.chatgpt.com/docs/app-server) and [ephemeral credential store](https://learn.chatgpt.com/docs/auth), verified against the pinned binary.

Each conversation has an isolated HOME/CODEX_HOME and an atomic, fsynced Hub-to-Codex thread mapping for each native identity. Old mappings and engine histories remain beside new ones. Native delegation, goals/automatic continuation, apps, plugins and user hooks are disabled and the effective configuration is checked. Shared person instructions and stdio MCP configuration are retained, including the conversation-bound Hub facade. Unsupported custom tool lists, settings translations, remote MCP shapes, triage and harvest launches refuse explicitly rather than weakening their restrictions. Codex's own sandbox is disabled only inside the required existing outer Hub box; the adapter never omits that wrapper.

Normal completed-turn continuation is supported. A dirty marker precedes every input write; failed, interrupted, disconnected or unverified histories cannot resume. `safeResume` stays false: no interrupted-tool replay guarantee is claimed. An empty thread is not materialized by this Codex build; only a durable clean `sent=false` mapping permits recreating that same empty thread. The runner may explicitly authorize a new native identity (including owner-selected `fresh_context`), which starts a separate mapping without resuming or replaying old input. The runner’s holds remain authoritative. A resume with missing or dirty state never falls back to a fresh thread. Thread token-counter deltas are used when available; missing usage stays null. Resolved backend model identity is not invented from the configured model.

## Validation and platform limits

Synthetic protocol/launch tests and a real Hub worker/store integration cover conversation isolation, explicit continuation, and a master restarted before receiving its first input. The actual pinned CLI completed two turns with a process restart on macOS and Linux ARM64 against a loopback-only Responses fixture. Both its MCP server and actual shell tool probed the parent processes for the synthetic provider key: macOS `KERN_PROCARGS2` and Linux `/proc/.../environ` could read those environments but found no key after the move to private RPC authentication. Positive controls exposed their own synthetic key. The proof also checked that session files contained no key and no `auth.json` was created. No paid model or live provider was used, and neither native delegation nor goal tools were advertised.

The macOS startup failure (`Failed to synchronize managed preferences`) is resolved by a Codex-only read grant for the exact OS shared-memory names `apple.cfprefs.<uid>v1` and `apple.cfprefs.daemonv1`. Both were required by the actual 0.160.0 binary; either alone failed before initialization. No preference-domain, preference-directory, credential, shared-memory write, or new host-control access is granted. Other adapters receive neither preference grant. The [managed configuration](https://learn.chatgpt.com/docs/enterprise/managed-configuration) mechanism itself is still honored; no managed-policy bypass is used. The diagnostic `codex-managed-preferences-unavailable` remains for unavailable configurations.

The shared Mac box grants specific installed Homebrew tool directories and the OpenSSL configuration needed by Node, with an explicit deny on Homebrew `var` (including its canonical path). The actual MCP proof could not read a newly created synthetic database sentinel there. No existing database files were inspected. The parent of a configured `outbound.accounts_file` is also a full-directory secret mask.

`bun live/prove-codex-box.ts --bin /absolute/path/to/codex` runs the actual pinned engine through the production outer box using a synthetic loopback Responses provider. It proves initialization, two completed turns across a process restart, Hub MCP execution, masked credential and other-person files, and confirmed process exit. It does not accept an unboxed mode, paid key, or remote endpoint. The proof uses disposable state only. The measured Mac runtime was Hub's Bun 1.3.14; Homebrew Bun 1.3.10 lost custom environment entries in the boxed Bun MCP child and failed this proof, despite the boxed shell retaining them. Use the measured runtime; no sandbox permissions were added for that separate runtime discrepancy. This is boxed protocol/tool evidence, not model quality, account entitlement, interrupted-turn recovery, or a production rollout. The same committed proof also passed on Linux ARM64 with Hub Bun 1.3.14 and a disposable official Codex 0.160.0 installation. Its first run timed out at the existing ten-second RPC boundary; diagnostic and restored exact-source runs passed without changing that timeout, so the initial cause remains unknown. The disposable package was removed. The Pi's global CLI remains 0.151.0 and is rejected by the pin; deployment must provision 0.160.0 separately.

No native transfer port is supplied. OpenCode retains its existing measured session-store/delegation capabilities and `safeResume=false`; its persisted sessions and successful ordinary continuation do not prove interrupted-tool replay safety. The movement lane separately retains the explicit missing-port refusal. This credential-transport proof covers Codex; other engines require their own credential-boundary validation.
