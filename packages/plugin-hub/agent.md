# hub - the household chat hub, version 3

> The fragment an operator session loads to know what the hub is, where its data lives and which commands to run. Wire it in with one `@plugins/hub/agent.md` line in `CLAUDE.local.md`. Delete the line to turn it off.

## What it is

People talk to their agents on Discord or Telegram, and no message is ever lost or silently ignored. One Postgres on the machine that runs the hub is the record and the queue. The operating system's service manager runs every process (systemd user units on Linux, launchd agents on macOS). An agent produces text, the machinery delivers it. A notification wakes a runner, and nothing polls on a timer.

The registry is the whole configuration: a hand-edited TOML file that lists every machine, person, credential, preset, agent and process. Nothing runs because it is on disk. It runs because it is on that list, and the hub notices an edit on its own tick with no restart.

## Where things live

- The registry: the path every unit is started with. On the owner's Pi it is `/srv/imprnt-hub/registry.toml`. The example with every key explained is `packages/plugin-hub/src/registry/registry.example.toml`.
- The store: the Postgres database `hub.store_url` names. Every role's password sits in `hub.secrets_dir` (`<hub.state_dir>/secrets` when unset), written by the database install, readable by the hub's account and by no agent's box.
- Chat logs: `<hub.state_dir>/<person>/chatlog/<agent>/<date>.jsonl`, one line per message in both directions, written by the door before anything is sent.
- Each person's tree: `[[people]].tree`, with the vault under `[[people]].vault`. An agent's box reaches its own person's tree and nothing else.
- Another machine's paths: a `[[machines]]` entry carries its own `state_dir`, `secrets_dir`, `store_url` (the hub machine's tailnet address) and `imprnt`; a person's tree, vault and instruction files there sit under `[[people]].on.<machine>`, a credential's file under `[[credentials]].on.<machine>`, and a repository's checkout under `[[repositories]].on.<machine>`. On a Mac the model login is a file made for the runner once with `claude auth login` pointed at that file's directory, never the owner's keychain item and never a copy of one. Every process reads the file for its own machine. `hub.store_machine` names the machine whose copy is the one: every hub writes the digest of its copy to the `registry` sheet, a spoke whose copy differs or whose authority has not written claims nothing (`check` says `registry-stale` or `registry-unseen`). An attachment's bytes go into the store's `media` table with the door's receipt, and a spoke's runner writes them into its own inbox before it feeds the row. The procedure for a runner on the owner's Mac is in `docs/operations.md`.
- Service logs: `journalctl --user --unit imprnt-hub-<entry>.service --no-pager` on Linux, `<hub.state_dir>/service-log/<entry>.{out,err}.log` on macOS.
- The spec and the operations notes: `packages/plugin-hub/docs/SPEC.md` and `packages/plugin-hub/docs/operations.md`.

## Commands

Every command takes the registry file. `imprnt hub` reaches them through the core's module dispatch. A core older than that dispatch prints its own help instead, and then the same verbs run as `node plugins/hub/hub.mjs <verb> <registry> [target]`.

- `check <registry> [machine]`: every finding for that machine, one line each with the fix as text. Exit 1 when there is one. Run it after any registry edit or when a chat is silent.
- `status <registry> [machine]`: wanted versus observed for every process the registry lists.
- `metrics <registry>`: the stamp metrics off the shared store.
- `install <registry> database | services <hub-entry> | entry <entry> | zone | --dry`: the database and its roles, then the units. Rerun `services` after an upgrade so the units carry what the new build expects.
- `recover <registry> agent:<id> | door:<id>`: replace one agent's session and release its claims, or restart a door so it reads its current token file.
- `relayout <registry>`: rewrite a registry written as one inline array per table into the header-per-entry layout the editor works on. Refuses a file that carries comments.

In a chat, an authorised sender can type `/recover <agent>`, `/dispatch <agent> <task>` and `/agent adopt|retire ...`. The board, reachable on the tailnet only, shows the same state and may edit the registry.

A council is run by an agent with the `hub_council` tool (`start`, `continue`, `inspect`, `stop`), never by the door on its own. `/council <question>` (`/совет <вопрос>`) is the owner's own message to the agent, marked with the command it began with: the agent asks who takes part when the message did not say, and starts the council on that message as its evidence. The roster is always explicit: each participant is a configured worker (an `[[agents]]` entry of that person with no door and no chat) with exactly the preset and machine its entry gives it, and a request that names anything else, or does not name everyone, gets the real choices back (`needs_participants`) and starts nothing. An owner's explicit request starts at once; an agent's own idea is shown to the owner as a frozen preview and starts only on their reaction. Every participant is an ordinary job with a conversation of its own, and a follow-up or a debate round is put into that same conversation. The council keeps its state in `council`, `council_participant`, `council_round`, `round_member`, `council_decision` and `council_event`; when every required answer is in, the hub writes one event row for the master, and the council is complete only when the master calls finalize from an attempt of its own and that attempt settles. A missing participant (an interrupted attempt, a refusal, a failure before it started) puts the council in `waiting_owner` with the cause named and nothing rerun, replaced or left out until the owner says so; a quiet or long-running worker is only flagged. One card per council is edited in place in its chat, and what needs the owner is said in that chat and in their General (`general` on the person's registry table, an agent id; with none, the council's own chat says so by name). The checkpoint (`council.checkpoint_minutes`, 30) blocks starting further work (a debate round, a retry, a replacement, the corrected input of a correction), never a running round. A correction after it is still accepted at once and the work it made outdated is asked to stop; only the corrected work waits, saved and named, for the owner's extension and for proof that the old process is gone. Runners speak protocol 3 with councils (a council's jobs and events cannot be claimed by an older runner); see `docs/operations.md` for the release order. A stop or a correction gates every job the council owns before it reads what is running, asks every running attempt to end, and supersedes an owner's retry that was still waiting for a process to be shown over; a council is stopped only when no attempt of any of its jobs is owned. A council that is complete or stopped starts work only through the owner's follow-up (a debate, a retry or a replacement is refused there). A participant is accepted with its effective profile (worker, preset and its settings, tools, file names, runner and machine) and every job of it is launched only while the worker still matches, and a worker that does not is refused by name and read as a missing member. The council's result is recorded together with the settlement of the master's reply, and a member's failure before its input is fenced by the transaction that ends the attempt. `check` reports `council-waiting-owner`, `council-waiting-master`, `council-finalizing`, `council-card` and `council-no-general`. A harvest slice, on the file and on the store, drops every council and watcher line the way both tails do.

The board has six pages, all built for a phone first: status, chats, people, usage, findings and metrics. It asks nobody to sign in: the tailnet is the boundary, the Host must be its bind address or one of the exact names its entry lists in `hosts`, a request another page sent is refused, and an act whose peer is the board's own machine is refused. The status page is the first screen: one sentence for the household, then one line per chat with the ones that need a person first (stuck and why, held, failing, busy answering since when, waiting to be picked up, paused, healthy), then `check`'s findings with commands to copy, and every machine folded to one summary line that opens to its table. It shows this machine live and every other machine's declared entries with what the store recorded about them (connected to the store now or not, a runner's last start, the last memory sample and its time, `check`'s findings, or `observation unavailable` when the store could not be read), never a state inferred from a missing finding. A card on the people page carries a sentence rather than a word: the finding's own words when `check` holds one about the agent or its door, otherwise where its open messages stand, each state counted on its own (answering only when the store shows a running attempt whose owner is current and connected; queued; held, waiting for a recovery choice, only while its hold is not released; unfinished with nothing working on it), with the reason for the oldest one, and `idle` when none is open. An original input whose hold the owner's recovery choice released is not current activity and is not shown at all. Under each person the people page lists what their agents may do, from the registry alone (machine, chat or jobs only, engine, the tool list as written, own MCP servers) beside the owner's approvals the `confirmation` rows hold for that chat. A `check` command shown on the board names a registry file that exists where the command runs, and says which machine that is: `recover` runs on the board's machine with its own file (and that machine named when the household has two routes to the store); any other command runs on the machine it names or the one that wrote the finding, with the file that machine's hub reported beside its registry digest, or, before that hub has reported one, an expression that reads the file off that hub's unit there. The pages are set in Golos Text with JetBrains Mono for commands and ids, both served by the board itself from `assets/fonts` (OFL, provenance in `assets/fonts/sources.json`). The chats page shows every person's chats and reads the door's chat log files on the board's own machine and no store row: every agent with its newest line, and one agent's chat newest day first and newest line first, two hundred lines a page with the older days a plain link away, text rendered as text with bold, code, fenced blocks and bare links kept. The usage page reads the turn records: per agent, turns, tokens and price today and over the last seven UTC days, plus every credential's newest plan window reading in the sheet's own words, and a nothing is printed as `-`, never as a zero.

A `[[run]]` entry of `kind = "watch"` is a program with no hands: on its schedule (`daily at 07:00` is a clock time on its machine, rendered as a calendar event on both service managers) it fetches one source with an `api-key` credential, compares with the `watch:<entry>` state sheet from the sweep before, and writes one notice into one person's chat through that person's agent's door. The one source is `source = "sentry"`: new issues at or over `notify_events`, issues whose event count moved a power of ten, and issues still open `reminder_days` after the watch first saw them, one line each, capped at thirty lines. A morning with nothing to say posts nothing and still writes its success stamp, so `job-stale` fires only when the sweep stops landing. A refused key, a bad answer, an answer with zero issues where the sheet holds rows, a count that is not a whole number or a continuation on another host exits 1 with `watch-failed: <entry>: <cause>` and leaves the sheet as it was. No model reads what it fetched: the digest's row and its chat log line are marked as a watcher's, the door delivers it and the board's chats page shows it, and both tails a session is fed leave it out.

The three hunt sources (`source = "kleinanzeigen"`, `"mydealz"`, `"vstdeals"`) are the same kind with their own keys: a folder of spec files (`specs`, one JSON file per hunt with a closed typed `hard` set, a closed `notify` set, a `lane` and an `owner` agent), an `audit` agent whose chat is the audit channel, and an optional `triage` master, an agent with `role = "triage"` that its runner launches with no tools, no MCP server and no instructions beyond the fixed triage text. Every tick, in code: fetch, drop what was seen with no change, re-evaluate a listing whose price changed (its audit row carries old and new, while a listing the person was already told about re-enters their chat only on a fall of five percent or across the spec's line, and a smaller move is `seen`), drop what fails a hard rule with the rule's name and the number it lost by, and the rest are hits. A notify hit is one notice to the owner's chat with zero model turns. A triage hit goes into one job row for the master, whose one-line verdicts (`tell`, `ignore`, `draft`) the next tick reads back: a `tell` reaches the owner, the other two are stored and audited, and nothing is ever sent to a seller. Every listing of every tick is one audit row in `<specs>/../../audit/<source>/<day>.jsonl` and, when the tick had anything but repeats to say, one notice in the audit chat. A refused spec file is audited every tick and is the `check` finding `watch-spec-refused`, and a job the master has not answered past the interval plus the grace is `watch-triage-overdue`. Every spec dark lands nothing and stamps nothing. One spec dark lands the rest as a partial sweep that removes nothing.

## Rules that always hold

- Never rewrite the registry by parsing and serialising it: comments are the only notes anybody has. Edit lines, or use the hub's own editor, which changes one line and proves the file still says what was asked.
- Every hub process that opens the store runs with `BUN_FEATURE_FLAG_DISABLE_SQL_AUTO_PIPELINING=1`. The units and `imprnt hub` set it. A script run by hand with `bun run` needs it on the command line.
- A message is answered exactly once, and every wait a person sees in a chat says why, from a closed list of reasons. A silence with no known reason is a `check` finding, never a vague sentence.
- The Pi is the box that runs the household. The Mac is where checks run and where a change is proved before it is merged. Nothing here writes to the Pi's live files without a command the report names.
